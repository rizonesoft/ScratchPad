# Review TODO Section

Grok runner. Do not open `.claude/skills/review-todo-section`. Host rules: `.grok/rules/campaign-runner.md`. You implement. Rounds 1 and 2 are `gpt-5.6-terra` at high effort. Round 3 is `claude-sonnet-5` at high effort and it signs off. A failed round falls back once to the other family. You do not sign your own stamp.

Shell is PowerShell. Scratch lives in `$env:TEMP\scratchpad-review`. Assemble prompts with `python3 .grok/scripts/assemble-review-prompt.py`. Execute producers only through `python3 scripts/review_prompt.py run`, which feeds the prompt on stdin and applies the wall clock. Do not wrap them in GNU `timeout`, and do not pass the prompt as an argv string. Python on Windows cannot start a bare `codex` name: resolve `codex` to the absolute `codex.CMD` from `shutil.which("codex")` and pass that path as the producer. `claude` resolves to `claude.EXE` the same way. UTC day for run ids: `[DateTime]::UtcNow.ToString("yyyyMMdd")`. If `python3` is missing, use `py -3`.

The gate between "code exists" and "the row says `[x]`". Nothing else may flip that row.

**Review is mandatory.** A `Verified:` stamp whose `Review:` line does not record real review work, with a committed findings file, is not a valid stamp. Self-review stays in-session, but the lens verdicts come from the mixed headless panel below (`gpt-5.6-terra` for rounds 1 and 2, `claude-sonnet-5` governing at round 3; a failed round falls back once to the other family), never from the implementing session alone: and the findings file is what makes that honest.

## Use this skill when

- A section was just implemented (`process-todo-section` ends by invoking this).
- The user asks "is §N really done?", "re-verify §N", "audit §N": run in **audit stance** (below).
- Before closing out a TODO file with `process-todo-file`.

## Step 0 -- resolve the argument

Same front door as `process-todo-section`. Never hand-translate a reference into a filename:

The section argument is the text after the skill name. Pass that string to `resolve`.

```powershell
python3 scripts/todo-graph.py resolve "<argument>"
```

Exit `3` means the row is already `[x]`. That is not an error here: it is the signal to run in **audit stance**, where the only permitted row change is `[x]` to `[ ]` on regression evidence.

## The three questions

Every review answers these with code and behavior evidence, never with assertion:

1. **Does it make sense?** Does the implementation produce the exact outcome the section asked for, without unnecessary scope?
2. **Is it logical?** Do the domain relationships, validation, calculations, permissions, UI behavior, and failure paths agree with each other?
3. **Did it break anything else?** Inspect callers, consumers, tests, and any adjacent workflow that reads what you changed.

Answer each by naming files and behavior. "Reviewed the changes, looks correct" is not an answer.

## Workflow

### 1. Map the evidence, then fix the candidate

For each checklist item marked `[x]` in this session, find the code that satisfies it. An item with no corresponding change is either not done (un-tick it) or was already true (worth a note).

Read the actual diff (`git diff`, `git show`), not your memory of writing it.

Then fix the **candidate**: the commit (or commit range) under review, recorded verbatim in the findings file with its hashes. A candidate nobody wrote down cannot be re-derived, and a review of an unknown candidate proves nothing. For an audit of shipped work, the candidate is the section's own commit(s), not the current tree: the tree has moved on.

### 2. Self-review

Work the three questions across the diff and its blast radius. Fix what you find, then re-ask them: a fix changes the answers. Self-review runs before the lenses, and it costs no round.

Look specifically for the failure modes this codebase is prone to:

- A trusted value decided in the UI with nothing verifying it.
- A file write that is not atomic, or a dirty flag that can disagree with the buffer.
- A permission or consent check the UI performs but the handler does not re-check.
- An encoding or line-ending path that assumes UTF-8.
- A protocol message built without schema validation.
- An agent-facing path with allow-by-default behavior.
- A frozen behavior that moved.
- A test that passes without exercising the behavior (mock that accepts anything, assertion on nothing).
- A UI surface compared against memory instead of the captured baseline.

Cheap defects caught here cost nothing; the same defect caught by a lens costs a whole round.

### 3. The lenses

Run each lens as a separate pass over the candidate, recording findings in the findings file (`docs/reviews/<domain>/D<NN>-T<NN>-s<N>.md`). Commit the findings file with the review.

| Lens | Asks |
| ---- | ---- |
| `adversarial` | How would this fail in hostile hands? Malformed input, races, injection, revoked consent mid-flow. |
| `consistency` | Does this agree with the rest of the tree: naming, patterns, shared styles, the settings store, the undo path? |
| `integration` | Do the callers and consumers still hold: shell/surface contract, transcript contract, session lifetime? |
| `source-defect` | When owed (a Notepad behavior or protocol detail is at stake): is the source read correctly, and is the deviation declared? |
| `design` | On a surface: judge the RENDERED surface against the baseline or contract, never source alone. Screenshots or driven captures, not impressions. |
| `record` | Is the record honest: does the stamp's evidence match what ran, do deferrals name owners, is the row flip earned? |

Each lens ends in a verdict: `approve`, `needs-attention` (with findings), or `advisory` (noted, not blocking). Findings are fixed in the candidate and the affected lens re-runs: iterate until no lens reports anything the plan would fix, under the soft-3/hard-5 caps below (the early sequence always runs whole before the Opus sign-off, which always runs because it governs the stamp). A unit patched three rounds running is stopped and re-thought instead of patched again.

### The mixed panel

Run the lenses through the mixed headless panel, with the candidate diff and the section contract inline (no tools needed, nothing to install): rounds 1 and 2 on `gpt-5.6-terra` at high effort, round 3 on `claude-sonnet-5` at high effort. `mixed headless panel` names that regime. Headings are `GPT panel` for terra and `Claude panel` for Sonnet on reviews stamped after 2026-09-22, because validation matches those words; pre-cutover records keep `Opus panel` headings and stay valid. The Telemetry model field carries the producer that ran.

Terra rounds (1 and 2, and any round whose Sonnet producer failed):

```powershell
$scratch = Join-Path $env:TEMP "scratchpad-review"
New-Item -ItemType Directory -Force -Path $scratch | Out-Null
git show <candidate> | Out-File -Encoding utf8NoBOM (Join-Path $scratch "review-diff.patch")
# Write the section text (Why, items with Done-whens, checkpoint) to section.md the same way.
python3 scripts/review_prompt.py fence PANEL "SECTION CONTRACT=$scratch\section.md" "CANDIDATE DIFF=$scratch\review-diff.patch" | Out-File -Encoding utf8NoBOM (Join-Path $scratch "fenced.md")
python3 .grok/scripts/assemble-review-prompt.py panel (Join-Path $scratch "fenced.md") (Join-Path $scratch "review-prompt.md")
$day = [DateTime]::UtcNow.ToString("yyyyMMdd")
$claude = python3 -c "import shutil; print(shutil.which('claude'))"
$codex = python3 -c "import shutil; print(shutil.which('codex'))"
python3 scripts/review_prompt.py run panel (Join-Path $scratch "review-prompt.md") <todo-path> <section> codex $day --timeout 900 --receipt-dir docs/reviews/receipts --candidate <sha> <findings-file> -- $codex exec -m gpt-5.6-terra -c model_reasoning_effort=high -s read-only -
```

(The prompt rides stdin: large diffs exceed argv limits as a positional argument. `--allowedTools` stays last: the flag is variadic and swallows anything after it. `Read` keeps the panel read-only; the diff and contract ride inline. Panel effort is `high` on both families. A `run` timeout or a nonzero producer exit fails that round over to the other family, once, per the outage matrix below. Do not add `--verbose` or `stream-json` to the producer: `check-panel` reads the plain verdict text. Token counts come from the run artifact's stderr tail when the producer printed `tokens used`, otherwise record `unknown`. The chunks ship through the `fence` subcommand (one randomness source; `$RANDOM` is a bash-ism that degrades under sh) because fixed delimiters are injectable from TODO text: only tagged lines delimit. Tags carry 64 bits of entropy, are collision-checked against every payload chunk with bounded retries before the prompt ships, and generation refuses rather than degrading on exhaustion. The output check validates the whole round (every lens exactly once, details only under non-approve verdicts, declared counts tallied); a FAIL is panel failure and fails over like a timeout.)

Sonnet rounds (round 3, Full rounds 4 and 5, and any round whose terra producer failed). Same prompt. Family `claude`. Record the verdicts under a `Claude panel` heading. Telemetry model is `claude-sonnet-5`.

```powershell
python3 scripts/review_prompt.py run panel (Join-Path $scratch "review-prompt.md") <todo-path> <section> claude $day --timeout 900 --receipt-dir docs/reviews/receipts --candidate <sha> <findings-file> -- $claude -p --model claude-sonnet-5 --effort high --allowedTools Read
```

(`--allowedTools` stays last: the flag is variadic and swallows anything after it. `Read` keeps the panel read-only. The model id is `claude-sonnet-5`, confirmed on this machine 2026-09-21. `-m gpt-5.6-terra` is the Codex slug, also confirmed that day, and `high` is one of its reasoning levels. `-s read-only` keeps terra from touching the tree. The `-` reads the prompt from stdin. A terra round is recorded under a `GPT panel` heading. A `GPT panel` section that is not the last panel section needs no outage note, because it is a planned early round. A `GPT panel` section that is last, because Sonnet failed and terra signed off, carries the words `Claude outage` naming the Sonnet failure (`Opus outage` before the cutover). Validator-enforced.)

The `run` subcommand wraps either rung atomically: `python3 scripts/review_prompt.py run <panel|plan> <prompt-file> <todo-path> <section> <family> <YYYYMMDD> [--timeout S] [--store DIR] [--receipt-dir DIR] [--candidate SHA] <scan-file>... -- <producer> [args...]` mints the run, executes the producer with the prompt on stdin under streaming byte, line, token (4096 chars), and wall-clock (600s default) bounds plus strict UTF-8 and NUL rejection, validates the output with the matching checker, stores the bytes content-addressed under ignored `build/review-runs/`, appends the run ledger, and prints the verdict with a `Provenance:` line (exit 0 PASS, 1 FAIL, 2 usage). Any bound kills the producer mid-stream with a naming diagnostic; a nonzero producer exit fails even with well-shaped output.

### Panel depth tiers

Cost follows blast radius. Record the tier and its reason in the findings file.

- **Full panel** (all lenses, soft cap 3, hard cap 5): the section's Adjacency names two or more consumers, or the diff touches shared contract surface (scripts, skills, settings store, undo path, protocol, test harness). Rounds 1 and 2 run on `gpt-5.6-terra` at high effort. Round 3 is the `claude-sonnet-5` sign-off at high effort. Rounds 4 and 5 run on `claude-sonnet-5` at high effort only for blocking findings (safety, data integrity, stamp-invalidating).
- **Light panel** (all lenses, soft cap 2): leaf sections with one consumer. Same rounds 1 through 3. A round-1 or round-2 `needs-attention` is fixed and the later rounds, including the sign-off, run against the new candidate. A sign-off `needs-attention` escalates to Full continuing at round 4 on `claude-sonnet-5` rather than filing follow-ups (the below-bar filing shortcut opens only at the Full round-3 sign-off).

Same-family circuit breaker: when a round reports only variants of an already-fixed root cause, sweep the family across the candidate, quote the sweep (command plus clean output), and run the next round as confirmation. One round per variant is the failure this rule exists to prevent.

Record the panel's per-lens verdicts verbatim in the findings file under a level-2 (or deeper) heading starting with the era's words (`Claude panel` after 2026-09-22, `Opus panel` before; a `Round N` suffix is fine; anything else, like `Round 2 Claude panel`, does not match), transcribed so each lens verdict sits on its own line as `` `lens` verdict `` (lens name immediately followed by `approve`, `needs-attention`, or `advisory`): the validator matches that shape per line, reading the LAST panel section as the record of verdict. Fenced code blocks are stripped before the scan, so quoting the panel shape inside a fence neither satisfies the rule nor displaces the real panel. Each verdict line must open (after up to 3 spaces) with a Markdown marker (`*`, backtick, `>`, `-`): mid-line mentions never count, so unheaded prose after an incomplete panel cannot supply its verdicts. Quoted headings are not structure: a fenced heading neither terminates nor displaces the panel. Quoted fences count as fences: a close must match the opener's quote depth, and a quote that ends ends its fence (a blank line ends the quote, so keep quoted fences blank-free). A backtick in a backtick-fence info string makes the line a paragraph. An unbalanced fence fails naming its opener line. The stamp's `Review:` line must name the findings file as `Raw findings: <repo-relative path>`: without it the validator cannot find the verdicts. A `needs-attention` verdict opens a fix-loop round: fix in the candidate, commit the fix, and re-run the panel against the NEW candidate diff with the prior verdicts appended (so fixed findings stay fixed and only live ones re-report). Panel findings carry per-round IDs (`R<round>-F<n>`: round of first report plus ordinal within the round, e.g. `R1-F2`); every fix-loop round dispositions each open ID as fixed (with the fix commit), live (still reporting), or filed (with the filed ref), and the sign-off records the final disposition table. The table shape is one Markdown row per open ID: `| ID | Disposition | Evidence |` where Disposition is fixed, live, or filed and Evidence is the fix commit, `still reporting`, or the filed ref. Round numbers run continuously across families in run order. The loop is bounded, never infinite: soft cap 3, hard cap 5. Rounds past the Full sign-off (round 3) run only for blocking findings (safety, data integrity, stamp-invalidating): a Full sign-off `needs-attention` whose findings all sit below that bar files each through `add-todo` and stamps without re-rounding, with the `Review:` line naming the filed follow-ups. Advisories reported by the sign-off round or later file through `add-todo` instead of re-rounding; advisories from earlier rounds stay noted in the findings file. A unit patched in 3 consecutive rounds is stopped and re-thought instead of patched again. If round 5 still reports `needs-attention`, disposition each leftover against the bar: safety, data-integrity, or stamp-invalidating findings stop the run and escalate to the operator with no stamp; below-bar leftovers file through `add-todo` (a new section, or an item on an existing section when small), record the filed refs in the findings file, and stamp with the `Review:` line naming the filed follow-ups: tracked work, not dropped work. The outage matrix: each round tries its assigned producer first, then the other family once for that round only. The next assigned round still tries its own producer. A failed terra round is recorded under a `Claude panel` heading from `claude-sonnet-5`. A failed Sonnet round is recorded under a `GPT panel` heading from `gpt-5.6-terra`, and when that section is last it carries the words `Claude outage` naming the Sonnet failure (no CLI, auth failure, model error, or timeout; `Opus outage` before the cutover). When no `GPT panel` section contains a lens verdict, stamps dated after 2026-09-19 require the era's note (`GPT outage: gpt-5.6-terra <what failed>` after 2026-09-22, `Sol outage:` before): the validator matches the era's words, and the note names terra. Pre-cutover records keep the legacy words (`Opus panel`, `Opus outage`, `Sol outage`, `opus rung`) and stay valid. Post-cutover records carrying any legacy `Opus panel` section fire. The LAST panel section of either family governs. If a round's assigned producer and its fallback both fail, stop: a session-only lens pass is not a substitute, and an outage with no verdicts from either family does not earn the stamp. Reviews stamped after D00 T01 §39 carry one telemetry line per panel round under its panel section, beside the verdicts: `Telemetry: round <n>; model <name>; effort <level>; duration <Ns|unknown>; outcome <worst verdict>; tokens <n|unknown>`, bare at column 0 with no Markdown marker (unlike verdict lines, which require one; marked or indented lines count malformed and do not parse), where the round is the panel round number continuous across families, outcome is the round's worst lens verdict (`needs-attention` over `advisory` over `approve`), tokens counts input plus output with cache lines in input (`unknown` when the runner gave none), and duration measures the producer's wall clock (`time` or run start/end instants, else `unknown`). Capture without transcription: the codex stderr tail (`tokens used` plus the count, commas stripped) or `--json` events, and claude `-p --verbose --output-format stream-json` (verbose is required: without it the flag errors) reading the `result` event's `usage`. The §39 review is the first live user. (No validator leg checks presence yet; the shape parses where present, and past records without lines read as unknown rather than zero.)

### Architecture gate

On sections touching editor state, storage, extensibility, AI integration, protocol, or consent/undo surfaces, blocking architecture rounds run after panel-close and before the stamp, outside the panel's soft-3/hard-5 caps with their own budget of one round plus one rerun. Every review writes trigger lines in the findings file, one per triggered surface, or a single `none` line when nothing triggers: `Arch trigger: <surface or none> - <scope or reason>`, where the surface is one of the six below and `none` carries the reason no surface applies (forward-scoped: reviews stamped after D00 T01 §38; earlier records predate the mandate and stay as written). The decision checklist: editor state (document, selection, or view state shapes change), storage (file formats, settings persistence, or migration paths change), extensibility (new seams, commands, or extension APIs), AI integration (agent, model, or prompt paths change), protocol (wire shapes, methods, or versioning change), consent/undo (permission boundaries or undo coverage change). When any item answers yes, the gate triggers on that surface; when several answer yes, the record carries one trigger line per surface and the round covers them together.

A triggered gate re-reads the candidate diff for significant design calls (state shape, storage format, extension seams, permission boundaries) through headless Claude Code on `claude-sonnet-5` at high effort, read-only, over the same fenced prompt plus one architecture-contract line naming the decision surface under review:

```powershell
python3 .grok/scripts/assemble-review-prompt.py arch (Join-Path $scratch "fenced.md") (Join-Path $scratch "arch-prompt.md") "<surface>"
python3 .grok/scripts/run-unchecked.py (Join-Path $scratch "arch-prompt.md") 900 -- $claude -p --model claude-sonnet-5 --effort high --allowedTools Read
```

(The producer is `claude-sonnet-5` at high effort, the same sign-off model as round 3. Return one verdict line as `**architecture: <approve|needs-attention>**` plus numbered findings naming files with line numbers. No output checker constrains it, so this round uses `.grok/scripts/run-unchecked.py` and a timeout exits 124. Do not send it through `review_prompt.py run`: that checker would reject a valid architecture verdict.)

When the Sonnet gate is unreachable (nonzero exit, auth failure, model-resolution failure, or a timeout), one `gpt-5.6-terra` high attempt runs over the same prompt, with the prompt on stdin because gate prompts carry the fenced diff:

```powershell
python3 .grok/scripts/run-unchecked.py (Join-Path $scratch "arch-prompt.md") 900 -- $codex exec -m gpt-5.6-terra -c model_reasoning_effort=high -s read-only -
```

(`-` reads the prompt from stdin. `-s read-only` keeps terra from touching the tree. The fallback round records under an `Architecture review` heading suffixed `(Arch-N terra-fallback)` with one line `Arch outage: sonnet-high - <what failed>` naming the failed rung. When the terra attempt also fails, the record carries `Arch outage: both rungs - <failures>`, the run stops with no stamp, and the operator owns the retry: an outage with no verdicts from either rung does not earn the stamp. Each Arch round attempts Sonnet first and falls back only on that round's outage: the fallback covers the round whose primary failed, never later rounds.)

Rounds number `Arch-1`, `Arch-2` (the rerun), outside the panel's round count and caps; each round records under its own `Architecture review` heading suffixed with the round (`(Arch-1)`, `(Arch-2)`), and the last round governs. The gate has no below-bar class: every architecture `needs-attention` is stamp-blocking, so an arch `needs-attention` blocks the stamp even when every panel lens approves. A `needs-attention` re-runs once after the fix as the next Arch round; a still-open blocking finding after the rerun stops the run with no stamp, never files-and-stamps: the record names the finding, the required redesign direction, and the operator as owner, and a redesigned candidate re-enters the panel as a fix-loop round and then the gate from Arch-1, because both rested on the superseded candidate. The `Architecture review` headings are not panel records (only `Claude panel` and `GPT panel` headings carry lens verdicts), and the stamp's `Review:` line names the gate rounds. Non-triggered sections skip the rounds but still write the `none` trigger line: absence of the line on a review stamped after §38 is a defect.

### Post-panel order

Panel, then architecture gate, then gates re-run, then plan review, then stamp, with the conditional steps in place: the panel (§3) closes first; the architecture gate runs on triggered sections; gates re-run (§4) follows the last fix; the surface check (§5, UI sections) and frozen check (§6, frozen TODOs) run where they are numbered; the plan review (§7) runs last before the stamp (§8). Blocking power per stage: the panel opens fix-loop rounds on `needs-attention` and stops the run on blocking round-5 leftovers; the architecture gate re-runs once on `needs-attention` and stops the run with no stamp on a still-open blocking finding; re-run gates must read green before the review proceeds, and a red gate reopens the candidate (fix, re-run the gates to green, and re-enter the panel as a fix-loop round, because the panel's verdicts rested on the broken candidate); the surface check refuses the stamp for an unaccounted control and the frozen check refuses it for a moved frozen behavior; the plan review is advisory and never blocks the stamp (a critical reopens the section through audit stance instead of riding the stamp); the stamp flips the row.

### 4. Re-run the gates

After the last fix, re-run the section's Test checkpoint and the owed gates (affected suites, warnings, analysis, `validate`). UI gates follow `.grok/skills/process-todo-section/gates.md`: focus-free default, focus-free Primary, and Interactive only inside 02:00-06:50 local. Quote the outputs. A fix verified by reasoning is not verified.

### 5. Surface check (UI sections)

Every control, menu item, dialog, and state on the Fidelity counterpart is working (proven on the rendered surface in this review) or deferred to a named, resolving section. Refuse the stamp for an unaccounted control. Compare the rendered surface against the baseline artifact or design contract before stamping, and confirm the user-guide update shipped in the same commit.

### 6. Frozen check (frozen TODOs)

Every `**Freeze check:**` in the section ran and passed, with the result quoted. No frozen behavior moved without a recorded operator approval. If one did, there is no stamp: there is a question for the operator.

### 7. Plan review

After the panel closes (before the stamp commit), one advisory round over the plan around the section: the section text plus its Depends and XREF neighbors plus its review dependents (direct reverse dependents, XREF-only consumers with a `-> XREF:` line to the section, and one transitive Depends hop past them; find them by grepping the ref across `todo/`), asking for gaps (a Notepad behavior no section owns), inconsistencies, faults, improvements, and premium wins. The hop bound is deliberate, not a gap: the manifest stays review-sized while deeper chains surface hop by hop as each layer reviews, so no chain is invisible, only ever one review away. The round never blocks the stamp: its feedback lands as tracked work through `add-todo` (micro/small items, new sections, new domains), synthesized by the implementing session, never applied blind. The stamp carries a `Plan review:` line naming the family plus the filings, `no findings`, `outage: <rung> (owner <name>, due <YYYY-MM-DD>) class <class> attempts <n> event <YYYY-MM-DD>` when both runners failed, `retry-owed (owner <name>, due <YYYY-MM-DD>) class <class> attempts <n>` on a same-family fallback run, or `partial: <rung>` when one rung failed and the other's findings stand (filings beside `partial:` are the survivor's; `partial:` names the failed rung, `gpt rung` or the era's sign-off rung (`opus rung` through 2026-09-22, `claude rung` after): the survivor owes `retry-owed (owner, due)` exactly when it is the same family as the sign-off panel, and a cross-family survivor carries no retry and no accountability fields); the validator requires it, and requires the grammar: the last marker line governs, `no findings` never sits beside filings, `outage:` never sits beside filings, `no findings`, `retry-owed`, or `partial:`, and `partial:` composes with `retry-owed` exactly when the survivor is the same family as the sign-off panel (normally the fallback; flipped under a GPT sign-off panel). Quorum: a complete review carries one independent second-family pass over the section. The sign-off panel is normally Sonnet, so the plan review's primary rung (gpt) is the independent family and the fallback rung (claude) is not; when Sonnet is unreachable and terra signs off under a GPT panel heading, the families flip (a GPT review is same-family there and owes `retry-owed` until a Sonnet pass supersedes). One surviving rung meets quorum when it is independent (cross-family to the sign-off panel): a cross-family survivor's findings stand on their own (no retry, no accountability fields, because there is nothing to own); a same-family survivor's findings file as tracked work but the review still owes its independent pass, so it carries `retry-owed` (owner, due) until a second-family rerun supersedes. The failed rung is named in the marker either way so the gap stays visible; the review stays advisory, so a forced same-family retry would spend a second run for findings that may duplicate the survivor's. The rule does not change: same behavior, one grounding (the missing independent review). Every outage, retry-owed, or partial line in the chain carries `class <class>` (failure class, open vocabulary) and `attempts <n>` (positive ASCII attempt count of 1-9 digits, whole token; validator-enforced), superseded outage lines included, so recurring failures are diagnosable from the record (bare partials carry detail but no accountability fields: the failed rung is still a failure). Attempt counts scope per marker line: each line's N counts the runner invocations behind that line's stated outcome (an outage line totals both rungs, a retry-owed line counts the fallback rung, a partial line counts the failed rung), the initial attempt always counts (N starts at 1, never 0), and reruns reset (each line counts independently; no cross-line arithmetic, so a rerun's attempts never continue its predecessor's). Worked fixtures: gpt fails once plus claude fails once then both fail again reads `outage: both rungs ... attempts 4`; a fallback run after one primary failure reads `retry-owed ... attempts 1`; a rerun after that outage reads its own `attempts 1`, not 5. Composite lines carry one `attempts` count per outcome in outcome order: `retry-owed ... attempts 2 ... partial: claude rung ... attempts 1` counts 2 fallback invocations plus 1 failed-rung invocation, never a blended total; worked fixture: that line reads exactly those two counts; a composite line with one count, a third malformed count, or counts against outcome order fires (count shape is validator-enforced, per-outcome truth needs run receipts like every other count). The class rides line-level or per outcome: one class names the whole line when both outcomes share the failure, two when each failed differently. Counts are author-asserted history: the validator checks shape (positive ASCII digits), never truth against run logs (no committed run receipts exist to recount from; cost of changing: committed receipts plus a cross-check); every outage line in the chain additionally names `event <YYYY-MM-DD>` (the calendar day the outage happened, a real date; validator-enforced, prose-outage excluded), so two outages of one rung on different days under one stamp key differently and a waiver for one never covers the other (same-day same-rung pairs still share a key); evidence rides the findings-file outage note and retry linkage is the `follows-outage` chain. Every marker over a review record carries its run, `(run <YYYYMMDD-DNN-TNN-SN-family[-rN]>)`, minted by the `run-id` subcommand (one generator: base from the TODO path plus section plus family plus date, `-rN` walking past claimed runs; mint it before the run with `python3 scripts/review_prompt.py run-id <todo-path> <section> <family> <yyyyMMdd> <findings-file>` where `<yyyyMMdd>` is `[DateTime]::UtcNow.ToString("yyyyMMdd")`, scanning the section's findings file where claimed runs accumulate (a genesis run passes no scan file; a missing scan file warns and reads as no claims)): the date prefix is the run's timestamp; within one date base the bare base is run 1 and `-rN` is run N for N >= 2 (numbering restarts per day, the date keeps runs distinct) (`-r1` accepted as run 1's synonym, never minted; comparisons read through it; `-r0` is outside the shape; non-ASCII or longer-than-9-digit suffixes fail the mint with a naming diagnostic). Genesis is a singleton marker (run, no supersedes); a rerun marker chains with `supersedes <prior-run>`, or with `follows-outage` when the immediately preceding marker is an outage marker (which carries no run to name); runs never repeat within a section, and the last run is one the manifest carries (validator-enforced). A rerun opens a NEW `Plan review` record with its own manifest, run, and ledger (reconciling §17's continuation rule with §19 runs: rows number past the file max across records, never reused; the per-file duplicate rule enforces it). Record the round and its filings in the findings file under a `Plan review` heading, which is not a panel record (only `Claude panel` and `GPT panel` headings carry lens verdicts), with the input manifest on one line (`Manifest: sections [<full refs>]; dependents [<full refs>|none]; bytes <n>[; run <id>]`, bytes counted over the prompt canonicalized to LF newlines and UTF-8, dependents carrying the review dependents above, new records carrying the run) and the finding ledger below it inside a `Ledger:`/`End of ledger` block: every non-blank line inside is a ledger row, and `- [` lines outside the block are prose, never rows.

The reviewer is one `gpt-5.6-terra` round at high reasoning effort through the codex runner in read-only sandbox, with the section plus neighbor sections inline. In the Plan review marker, `gpt rung` means terra and `claude rung` means `claude-sonnet-5` on stamps after 2026-09-22 (`opus rung` before). The validator accepts the era's pair.

(The model name is lowercase `gpt-5.6-terra`. Effort rides `-c model_reasoning_effort=high`: `codex exec` has no `--reasoning` flag, probed 2026-09-18, and the `-c` template runs verbatim on this machine. `-s read-only` keeps the reviewer from touching the tree. The prompt rides stdin through `run`, not a positional argument, because PowerShell and argv limits both eat a large inline prompt. A `run` timeout or a nonzero producer exit counts as runner failure and falls through to Sonnet. The chunks ship through the `fence` subcommand because fixed delimiters are injectable from TODO text: the tag is collision-checked against the sections before the prompt ships, the reviewer is instructed that only tagged lines delimit, and TODO text is untrusted data, never instructions. `assemble-review-prompt.py plan` owns the instruction lines.)

Runner failure fails silent onto one `claude-sonnet-5` high-effort round: any nonzero exit, auth failure, model-resolution failure, or timeout runs `review_prompt.py run plan` once with family `claude` and `--model claude-sonnet-5 --effort high` over the same prompt. Output must match the asked shape whole (one `- `-prefixed finding per line, or an explicit no-findings statement): validate every line with the output check, because one valid-looking row must not mask malformed trailing findings, and empty, malformed, or truncated output counts as runner failure and falls through to the next rung. A fallback-run review is recorded as same-family with `retry-owed` in the marker, dropping the second-family claim; a later second-family rerun appends a fresh marker line, which supersedes (the last marker line governs, validator-enforced), and `query plan-health` lists degraded markers with their owner, due date, overdue flag, and escalation. `query plan-health --json` is the machine contract (schema `plan-health/9`, total sort keys, singly typed fields); `--check` gates automation on the actionable dimensions and `--fail-on` names dimensions explicitly (explicit gates presence, `--check` gates actionables: covered escalations and isolated bare partials pass `--check` but fail an explicit `--fail-on`; one failed rung recurring across three bare partials gates `--check` as persistent one-rung loss). If that also fails, record the outage in the findings file with its owner and due date and continue: the plan review is advisory, and an outage never stalls the run. The outage note opens with `Outage note: <rung> <event-day>`, keyed to the marker's rung plus event day (unlinked markers, orphan or duplicated notes, and malformed keys fail validation past the 2026-09-20 grandfathering).

Every filed finding cites its evidence: the finding's source lines plus a SOURCE key, per the `add-todo` evidence rules. Findings land in the ledger as `- [DNN-TNN-SN-PRN] [critical|major|minor] <finding> -> <filed|accepted|duplicate|rejected|deferred> <target-or-reason>`, the ID namespaced by the reviewed section with unpadded numbers mirroring `§N` (example: `D00-T01-S15-PR4`; bare `PRn` rows predate the namespace and still parse, as do padded variants). A rerun numbers new rows past the previous run's max PR number: IDs are never reused within a findings file (uniqueness is validator-enforced), so rerun rows cannot collide with superseded ones. Count in accepted findings versus implementation items: an accepted finding is one triaged ledger row, an implementation item is one checklist line, and a merge (two findings, one item) states both numbers. A clean round still writes its record: `no findings` in the marker plus one ledger line (`- [DNN-TNN-SN-PR0] [minor] clean round -> accepted`). Advisory never blocks except when it must: a finding that invalidates safety, data integrity, or the stamp reopens the section through audit stance instead of riding the stamp.

Ledger discipline, transition table first: triage sets accepted, rejected, or duplicate; accepted moves to filed when the todo commit lands, or deferred with an owner, a due date, and a trigger; deferred moves to filed on trigger. History enforces it: `filed`, `rejected`, and `duplicate` are terminal against the committed record, and later evidence against a terminal row lands as a NEW row naming the superseded ID (`supersedes <finding-id>` after the disposition plus `identity <12hex>` proving the target (sha256 over its normalized subject, severity, and disposition; missing or mismatched tokens fire, and unrelated same-namespace rows cannot link without one); the validator enforces target existence, same-namespace equivalence, acyclicity, the identity proof, and a non-empty head rationale (restate everything, inherit nothing: severity plus disposition ride the grammar, deferred heads restate owner/due/trigger, filed heads name their own targets, any disposition may head any target), and plan-health reads the un-superseded head of each chain as current) (amendment by supersession, never by editing the old row); a row that vanishes fails the same way. Severity: critical invalidates safety, data integrity, or the stamp (and triggers the audit exception above); major is wrong plan behavior; minor is polish or wording. Every open critical or major carries its owner and accountability date: accepted rows use `(owner <name>, due <YYYY-MM-DD>)`, deferred rows use their `owner <name> due <YYYY-MM-DD> trigger <t>` triple. Exception: rows in grandfathered pre-cutoff records are exempt from the owner shape (rule 18 is date-scoped; they list with `owner ?` and still fail `--check` while uncovered); the exemption rides the stamp's grandfathering, which the migration retires by 2026-12-31 (D00 T01 §21 item 3), past which leftover batches fail `--check` on the grandfathered dimension. Filed findings link both ways: the target section's SOURCE key names the finding ID (example: `-> SOURCE: plan-review-D00-T01-s15-2026-09-18 D00-T01-S15-PR4`), and a filed critical clears only when the target also names `fix <sha>` (a non-merge commit that touched the target file and whose tree contains the ID; multi-commit loops name `fix <base>..<tip>` with the tip tree carrying the ID, the tip descending from the base, and a touch inside the range, base excluded so the base is the pre-loop tip), binding fix-commit attribution to the target's post-finding stamp. Ordering reads Duration ends when both reviews carry them (same-day fixes order by completion instant); without both ends the day-stamp rule applies and same-day fails closed. Ranges are needed exactly when clearance must order inside one day, and the normal same-day loop qualifies without a mandate: `Started:` at implementation start ranged to stamp completion, with rule 26 (`duration-range-uncheckable`) tying both ends to those dates on post-cutoff stamps. Every unresolved critical names its failed clearance leg in text (`failure <leg:site>`) and JSON (`failure_code`); accepted and deferred rows never ran clearance and carry none. The fix committer timestamp must postdate the review completion with the same day fallback, and the target names `proof <finding-id> <path>[::<test>]` resolving at the fix tip tree; bytes prove attribution plus the named proof, not remediation, whose proof is the target's own review and stamp. The review's recorded candidate must be an ancestor of the fix (causal history, not wall clocks alone; records predating the provenance mandate carry no candidate and skip the leg). An overdue degraded marker escalates to the operator: rerun the review (a superseding marker) or record risk acceptance in the findings file. An open finding past its due date escalates the same way: remediate it (file the row) or record risk acceptance; the query prints `OVERDUE escalate operator` on the row. `query summary` names the noncoverage cause plus its fix on every uncovered entry (`no-waiver`, `predated-target`, `predated-evidence`, `foreign-evidence`, `stale-generation`, `missing-target`, `post-dated`, `stale-evidence`, `git-unresolvable`, `expired`, `terminal-outcome`; superseded records skip silently since succession is same-target and the head's verdict governs). A risk acceptance is one line in the findings file carrying the escalation: `Risk accepted: <target>; id A<n>; approver <name>; owner <name>; date <YYYY-MM-DD>; expires <YYYY-MM-DD>; review <YYYY-MM-DD>; evidence <40-hex>; [generation <n>;] [supersedes A<n>; outcome <renewed|remediated|rejected|closed>;] [action <text>;] rationale <text>`, where the target is a finding ID, a run ID, or `outage <rung> <date>` (the rung plus the outage marker's event day, binding the instance: a later outage of the same rung is never covered by an earlier waiver); the id is a positive file-scoped serial and the supersession identity (the record date stays ordering metadata, never identity); `supersedes` names the predecessor id and arrives paired with its `outcome` (one optional group, so the pair is atomic); `action` is optional and semicolon-free, beside the human rationale; the evidence is the full 40-hex id (peelable to its commit for the lineage leg; peel-identity deliberately not required per D00 T04 §6 item 2, since no reachable construction distinguishes tag evidence from commit evidence); expiry never predates the record date, the review date sits inside record..expiry (bounds inclusive), and the rationale rides last so it may contain semicolons. Trust model: owners and approvers are free-form accountability labels under a single-operator default (one writer on trunk; a name binds a human to follow-up, never an authenticated identity, and nothing validates that a name maps to a real operator). Cost of changing it: an identity registry plus approval thresholds, which would turn every owner and approver field into a lookup. An acceptance covers while today sits between its record date and its expiry (expired or post-dated is uncovered, and the escalation persists loud); an acceptance in a findings file attached only to pre-cutoff stamps covers nothing (rule 24 never validates it, so the query never consults it). Coverage additionally needs the record generation to equal the section generation (absent reads 0; else `stale-generation`), the target to predate the record (run date prefix, outage event day, or the finding's review day; same-day-or-later passes additionally need the target present in the evidence commit's bytes, else `predated-evidence`), the evidence to descend from the reviewed candidate (both peeled to full commits first; proven foreignness only, else `foreign-evidence`), the target's own lines to still read as the evidence commit saw them (finding rows by id, marker lines by run or rung-plus-event; LF, trailing-whitespace-stripped, acceptance lines excluded: the record cannot cite a commit that already contains it; any target-line change voids while unrelated edits stay silent; renewal rides a superseding record), and no superseder to have replaced the record. Amendments ride superseding records only and append-only is absolute: a record edited or deleted fails against history like a ledger row (the predecessor stays byte-identical next to its successor), and self-links, cycles, double successors, duplicate ids, cross-target succession, and forked heads fail as broken chains. An expired match escalates to the acceptance owner (`<owner>: renew the acceptance or rerun/remediate`; a post-dated match stays operator-escalated), and covering acceptances (live escalation on the target's dimension: minor-row and healthy-marker waivers list nothing) near or past their review date surface in the plan-health `reviews` dimension (review-due warns, review-overdue fails `--check` and clears only through a superseding record whose rationale is the review outcome). A covered escalation clears its OVERDUE, its escalation, and its gate vote, and shows `accepted by <approver> owner <owner> expires <date> review <date> rationale <text>` where the escalation lands, plus `outcome <enum>` when the covering record supersedes (all six ride the JSON record too, the outcome as `accepted_outcome`, empty when the record stands alone). Outcomes read as a matrix: `renewed` continues coverage under the successor (next review at the successor's review date), `remediated` continues until the row files (the debt being gone obligates filing, not renewing), `rejected` terminates (the escalation returns to unhandled), and `closed` terminates (the target is out of scope); a matched `rejected` or `closed` record voids even when every leg passes (`terminal-outcome`), and no outcome narrows (narrowing rides a fresh waiver with a narrower target plus a same-target superseder with outcome `closed` ending the broad scope; a cross-target superseder is chain-broken, and the broad finding stays uncovered until its row resolves).

### 8. Write the stamp and flip the row

Append the stamp block at the end of the section: `Verified:` (date, coverage, quoted evidence), `Review:` (rounds, candidate fingerprint or hashes, per-lens verdicts, findings-file link), `Plan review:` (family plus filings or `no findings`), `CRUD:` (behavioral evidence or an honest not-applicable), plus `Duration:` (minutes or `<start> to <end>` Zulu range, whose end orders clearance) and carried `Deferred:` lines, plus `Reviewed-tip:` (`> **Reviewed-tip:** <full-40-hex>`: the tree the review attested, minted with `git rev-parse HEAD` at review time; clearance binds the fix tip to its history, and sections stamped before §55 stay unbound without it). The findings file carries a `Live proof` section quoting the section's gates: each command run and its output, so a later auditor reads candidate-bound evidence without reconstructing Git history. Every live quote carries its provenance on one line (`Provenance: candidate <full-40-hex-sha>; command <cmd>; exit <n>; tool <name version>; digest <sha256>; path <repo-relative primary reviewed artifact>; run <id>`), digesting the quoted output so the artifact, not memory, backs the claim. Resolve the candidate at mint time (`git rev-parse <sha>^{commit}`) and record the peeled commit ID: shorts in runs dated after 2026-09-19 warn, a recorded full ID that is not a commit fails, and history growth can ambiguate anything less. Name the primary reviewed artifact as the path, as a canonical relative path with no `..` segments (it must be a regular file in the candidate tree on new records; findings-file self-paths are legacy and keep checkout existence). Fields ride semicolon-separated and carry no bare semicolons; run-less provenance fails the shape on new records. On post-cutoff records the validator additionally requires a candidate resolving to a commit, a contained repo-relative path, and a run equal to the section's last marker run; unprovable git degrades to a baseline-tracked warning instead of skipping silently; runs after 20260921 recompute the digest as the sha256 of the path blob in the candidate tree, and earlier lines stay attested. Stamps on or before 2026-09-18 predate the mandate and skip, per the §21 inventory (57 run-less pre-cutoff files, owner operator, deadline 2026-12-31). Raw reviewer outputs ride fenced in the findings file (fences strip from every scan), so output-check PASS claims stay checkable against an artifact instead of an ephemeral `/tmp` file. Then flip the Implementation Order row to `[x]`.

Re-verification replaces the stamp in place, except `Plan review:` marker lines, which append (marker history is append-only: a rerun adds its line and the last marker governs, never rewrites). Never accumulate duplicates, and never edit a stamp to fit new code: the fix goes forward in a new commit and the stamp is rewritten by review.

### 9. Audit stance

On an already-`[x]` section: run steps 1-6 against the section's own candidate. Confirm the stamp's evidence still holds (re-run the checkpoint), or find the regression. The only permitted row change is `[x]` to `[ ]`, with the reason written into the section as a blocking note. A critical finding reopens through audit stance by adding a `> **Reopened:** <YYYY-MM-DD> | generation <n> | <finding ref> | <reason>` line naming the audit locus (the generation is previous-plus-one of the stamp generation, and the re-stamp persists it, so no old acceptance revives when the line lifts), unchecking the row (the stamp is void everywhere downstream), and parking every stamped section downstream in the Depends closure until the root re-stamps, bottom-up; the validator enforces the shape, the unchecked row, and the parked cascade. A re-confirmed row keeps its stamp; say so in one line.

## Guardrails

- Do not stamp without a findings file. A verdict with no record is an opinion.
- Do not stamp an unaccounted control on a UI section.
- Do not stamp a frozen behavior that moved without approval.
- Do not flip a row this review did not earn.
- Do not review the working tree when the candidate is a commit. Name the hashes.
- Night debt is stampable: stamp a debt-carrying candidate when its focus-free proofs are green (never-park: quiet time never holds a stamp). The `Night-owed` line plus the collector runbook is the owed proof's address, not a gap; only the true flip blockers (red focus-free or Primary proofs, unmet Depends, missing baseline artifact, unreachable host, both review families down) hold the stamp.
