## Self-review

1. Does it make sense? Yes. Every checklist item has its drive; the checkpoint (encoding matrix byte-identical, failure and external-change paths driven) is the FileOpen suite at 37/37. No scope beyond the section: messages, the filter spec, and the watcher all serve named items, and the rendered dialog plus picker application are explicitly handed to D01 T02 §1, which owns the first open trigger.
2. Is it logical? Yes. Failures funnel through `MapFailure` (unknown exceptions and cancellation propagate, never map); the OS message rides in `OpenFailureResult.Detail` for Unreadable; `OpenFileAsync` never touches `TabModel`, so a failure cannot add a tab; the size gate refuses before allocating; ties break CRLF, LF, CR with empty defaulting CRLF, matching the recorded rule.
3. Did it break anything else? No. Full suites green on both OSes (Windows slnx: Smoke 1/1, Unit 89/89, Protocol 35/35, UI 18/18; Linux slnf: Smoke 1/1, Unit 89/89, Protocol 35/35); `OpenFailureResult`'s new optional `Detail` has no other constructors in the tree; `TabModel.OpenTab` is additive with no prior callers.

Round-1 finding (fixed in `5c28ed3`): a file past `int.MaxValue` bytes with a large `MaxBytes` threw `OverflowException` from the array allocation instead of refusing; the gate now refuses as `TooLarge`, driven over a sparse file.
