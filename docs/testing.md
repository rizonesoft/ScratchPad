# Testing

Unit, smoke, UI-automation, and protocol tests each have a harness under `tests/`, and one `dotnet test src/ScratchPad.slnx` run executes every suite (`src/Notepad.Neutral.slnf` filters the neutral scope for a fast check). The run includes the fenced interactive UI tests (below) plus the Category=Primary placement set, and each skips unless its safe context holds: the fenced set runs only inside the 02:00-06:50 window (or with SCRATCHPAD_INTERACTIVE_FORCE=1), owning the foreground while it runs, and the Primary set runs only under SCRATCHPAD_BACKGROUND=1 (or in the window/forced), so outside those contexts the run reads green-plus-skipped; the per-section gate is the default-filtered run, which never takes the foreground.

## Framework

xUnit v2 with the VSTest runner: `Microsoft.NET.Test.Sdk` 17.14.1, `xunit` 2.9.3, `xunit.runner.visualstudio` 2.8.2, pinned per project with lockfiles. Every test project targets `net10.0` and references only neutral libraries, keeping the suites OS-independent; Windows-only coverage comes from the UI suite driving the real binary.

xUnit v3 with the Microsoft Testing Platform runner was evaluated twice and ships nowhere: T01 §5 proved zero-test discovery on our project and xUnit's own template across many configurations, and the T02 §1 re-evaluation reproduced it on the current vendor `xunit3` template (`xunit.v3.mtp-v2` 4.0.1) retargeted to `net10.0`, where a real `[Fact]` reports `Zero tests ran` with exit code 5. Re-evaluate only when a new v3 or template release claims the discovery path fixed.

## Suites

`tests/Smoke/` holds the one wiring test that proves the harness works; `tests/Unit/` holds unit tests over the neutral libraries, starting with the framework-choice tests. `tests/UI/` drives the stub window under FlaUI (launch, title assert, close, with a failure screenshot); the ACP loopback fixture (T02 §4) arrives with its section. Test-only helpers shared between suites live under `tests/Common/` per its README.

## Commands

Run everything for the host OS with the `dotnet test` commands above. Run one suite with `dotnet test tests/Unit` (or `tests/Smoke`, `tests/UI`). Filter within a run with `--filter`, for example `dotnet test <solution> --filter Smoke`. Test output uses the default console logger; anything written under `TestResults/` is gitignored.

## UI suite preconditions

The UI suite drives real windows and native dialogs, so two machine settings must match the golden-capture environment: dark app theme (`AppsUseLightTheme` 0, else goldens mismatch) and visible file extensions (`HideFileExt` 0, else dialog prefill reads, file-list names, and save routing shift and 6 MenuBarTests fail). Verify with `(Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Themes\Personalize').AppsUseLightTheme` and `(Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Advanced').HideFileExt`. (CI set both before its test step until 2026-09-17, when UI tests left CI; the settings still gate local runs.)

## Uninterrupted gate (D00 T02 §8)

Default run, background-safe: `dotnet test tests/UI --filter "Category!=Interactive&Category!=Primary" -e SCRATCHPAD_BACKGROUND=1`. The `-e` flag is load-bearing: it is the only channel that reaches the app through the test host (shell exports do not propagate, measured 2026-09-17), and it makes every window start minimized. The suite then moves each window to the secondary monitor (off-screen on single-monitor boxes) and drives it through UIA patterns: visible there but never activated, so no foreground and no cursor. Fenced run, visibly on demand: `dotnet test tests/UI --filter "Category=Interactive"` with no `-e` flag. Fenced tests own the foreground and the cursor (physical keys, drags, dialog clicks), so run them when the interruption is yours to spend. Placement run, focus-free on the primary: `dotnet test tests/UI --filter "Category=Primary" -e SCRATCHPAD_BACKGROUND=1` with the foreground log under `--expect-primary`; its windows show where the app put them (geometry and cascade premises) without ever activating.

Foreground proof rides alongside the default run: `Bin/ForegroundLog/Debug/ForegroundLog.exe <seconds> <logpath>` polls the foreground window and exits 1 naming the run red if ScratchPad ever held it. Green means the default suite passed with zero failures AND the log flagged zero foreground holds; a passing suite with a flagged log is a gate failure (some test activated a window). The same run records a census of every app HWND (monitor, rect, iconic state) and a placement-event log of each window's first visible bounds (EVENT lines from show and location events). It fails when any window rests on the primary monitor or when a primary birth shows up in the event log; iconic, invisible, and zero-area windows are recorded but excluded. Placement is by rect intersection (off-screen reads offscreen, never primary). Resting still means seen twice on the census. The event log records the birth even when that flash never spans two polls, and the gate is green only when every placed census window has an event and the two reports agree on zero primary births. A window may rest on the secondary monitor after an off-screen birth; that still agrees. Primary on only one side does not. The fenced set is green when it passes visibly, and the placement set is green when it passes with its census on primary and the event log agrees the birth was on primary. The input audit behind the split lives in `docs/ui-input-audit.md`.

Quiet hours hard-gate the fenced set: every `Category=Interactive` test runs under `[InteractiveFact]` (or `[HookFact]`, which composes the same gate with a hook-availability probe), which reports Skipped outside the foreground window (02:00-06:50 local, operator schedule 2026-09-17), so even an unfiltered daytime run cannot interrupt. `SCRATCHPAD_INTERACTIVE_WINDOW` (`HH:mm-HH:mm`) moves the window and `SCRATCHPAD_INTERACTIVE_FORCE=1` runs regardless for an explicitly accepted interruption; unparseable config fails closed to skip. Reflection guards pin the pairing both directions (`QuietHoursTests.EveryGatedTestCarriesTheInteractiveTrait` plus `EveryInteractiveTraitCarriesAGate`). A daytime full-solution run reads green-plus-skipped, never fully proven; only the nighttime run executes the fenced set.

## Birth rule (D00 T02 §11)

Backgrounded launches birth off-screen: `UiLaunch.SeedSettings` seeds X/Y 10000 whenever `SCRATCHPAD_BACKGROUND=1` and the caller left geometry at the 50/50 defaults, so the first window restores where no census line can call it primary and no birth flash ever paints on the primary. ForegroundLog writes one EVENT line per window at the first visible show or location event, and the gate requires that line's monitor class to match the census. Explicit geometry always wins: any X/Y the caller set survives seeding, which is how the Primary set keeps its on-primary premises (both Primary tests seed explicit rects). All five launch helpers (`LaunchApp`, `LaunchAppWithArgs`, `SeedSettings`, `SeedSettingsFile`, `AppExePath`) live in `tests/UI/UiLaunch.cs` only; per-file copies are removed, not wrapped. `SeedSettingsFile` is the path-returning seed for callers that own their own cleanup; it applies the same background rule. The funnel (`UiForeground.Background`) stays as the safety net for unseeded paths: redirect-created windows and direct launches still birth at the cascade, so show-then-move with sleep-after-move keeps covering them.

## Fence-with-proof rule (D00 T02 §8 item 12)

A test is fenced only with a quoted background-fail plus foreground-pass pair: run it backgrounded (the default run with `-e SCRATCHPAD_BACKGROUND=1`) and quote the failure, run it foreground and quote the pass, and cite both in a `// Fenced:` comment on the test. A fence without its pair is a guess, not a gate. The 28 fences shipped with §8 predate the rule and carry grandfather notes citing the audit (`docs/ui-input-audit.md`) section or mechanism instead; a grandfathered fence that is ever un-fenced and re-fenced owes the pair like any new fence. Two placement-premise tests (geometry restore, cascade) moved to the `Category=Primary` set with cited pairs instead of fences under the item 7 revision.

Interruption-risk exception (D00 T02 §21 item 1): a test whose physical press passes backgrounded still stays fenced when the press itself takes the operator's foreground (a physical key needs focus, so `UiInput.Press` activates the window and would steal it from whoever is typing). Its pair is the backgrounded-forced pass plus the foreground pass, and its `// Fenced:` comment cites this exception by name instead of a background failure. Today it covers `AcceleratorTests.ChordCtrlShiftGOpensStats`, `ChordCtrlShiftHOpensSnapshots`, and `ChordCtrlShiftXOpensExport`. The exception never admits a test that could run through UIA patterns instead: only a test whose point is the physical press qualifies.

## Ship-with-debt gate (D00 T02 §10)

A daytime gate is complete with debt: default run green plus placement run green plus the Interactive skip count with its debt id is a complete gate, and the collector closes the debt async. Concretely: the default suite passes with zero failures and a clean foreground log, the Primary set passes with its census on primary, every Interactive test skips with the quiet-hours reason, and the skip count matches the `Night-owed` count the section recorded; the section flips the same session and never parks on quiet time. The debt id travels in the section's `Night-owed:` line and the morning report's Night debt section proves the collection; a red collection reopens through triage, never by holding the flip.

## Nightly regression run (D00 T02 §9)

The nightly run is the governed full-suite proof: three legs inside the 02:00-06:50 window, owned by the `\ScratchPad\Nightly UI` scheduled task (daily 02:30 local; action `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "R:\GitHub\ScratchPad\tools\NightlySupervisor.ps1"`, Start In the repo root, Run As DerickPayne, multiple-instances IgnoreNew, 4-hour limit, wake-to-run, interactive-token logon; all read live 2026-09-20, task operator-owned). The action runs the outer supervisor (D00 T02 §15, D00-T02-S14-PR1), which watches the run with a 14280 s timeout (PT4H minus 120 s) and publishes a minimal RED tombstone (`Status: supervisor tombstone`) when the run hangs or exits without publishing; a fresh report always stands and the supervisor relays the run's exit code, and a second supervisor stands down on its own mutex (the scheduled IgnoreNew equivalent). A manual run (`powershell -ExecutionPolicy Bypass -File tools\NightlySupervisor.ps1`, or `tools\nightly.ps1` directly with `-Force` outside the window for an accepted interruption) is the backup when the trigger is missed. The sibling `\ScratchPad\Nightly Foreground Single` task (daily 02:05, one foreground test) predates this procedure and stays outside it.

Pre-flight reaps orphaned test apps (and test hosts) whose executable lives under this checkout's `Bin/`, logging each pid plus start time; a released ScratchPad anywhere else is never touched. Leftovers from a dead run hold Bin locks (MSB3027 on the next build) and their stale windows contaminate window-enumerating tests, so the reap precedes the run at pre-flight (live-leg kills moved to job objects). A named mutex (`Global\ScratchPadNightlyRun`) serializes governed runs: a second invocation stands down with exit 0, and the reap only takes processes older than the run's own start, so overlapping runs can no longer reap each other.

Run A (default leg): one `dotnet test tests/<proj>/<proj>.csproj` per test project (Smoke, Unit, Protocol, UI) under the same gate window, `--filter "Category!=Interactive&Category!=Primary" -e SCRATCHPAD_BACKGROUND=1`, each keeping its own `run-a-<proj>.trx` (D00 T02 §15, D00-T02-S13-R2-F2: a shared solution-level trx name overwrote every project but the last), with `ForegroundLog 1800 <gate-default.log>` alongside (built first from `tools/ForegroundLog/ForegroundLog.csproj`, which no solution includes). Green needs the suite passed with zero failures AND the gate exit 0 (zero foreground holds, zero resting primary windows, zero primary births in the placement-event log, and the two logs agreeing). The gate window intentionally overruns the suite (~13 min) so the whole run stays covered; the idle tail is designed waste, and a suite that overruns its window is killed at the bell, fails the leg, and has its tree reaped (partial proof is no proof; the timeout is enforced, not a stopwatch).

Run B (primary leg): `dotnet test tests/UI --filter Category=Primary -e SCRATCHPAD_BACKGROUND=1` with `ForegroundLog 300 <gate-primary.log> --expect-primary` alongside. Green needs the suite passed AND the gate exit 0 (zero holds, at least one window resting on primary, and the placement-event log agreeing that the birth was on primary).

Interactive leg (collection): `dotnet test tests/UI --filter Category=Interactive` with no `-e` flag, owning the foreground. Green needs every collected test passed; the excused skips are quarantine skips (T02 §5 procedure) plus capability skips (host lacks hooks or a usable spooler: `HookFactAttribute`, `PrinterFactAttribute`), and quiet-hours skips fail the leg (the run owns the window, so none are excused). Enforcement is mechanical: after the leg, any skip without a QUARANTINED stamp (date plus id) or the `CAPABILITY:` reason code reds the run (the exit code alone cannot prove it, since xUnit exits 0 under skips); a missing or malformed trx is unproven and reds the run; legacy un-coded capability messages match by prefix as fallback only.

Logs land under `build/nightly/` (ignored scratch, never committed), scoped per invocation: leg transcripts `YYYY-MM-DD-HHmmss-{default,primary,full}.log` (the full log carries the Interactive collection), with the suites' stdout in `.out.log` siblings the report's Log cells name (D00 T02 §22 item 5): `YYYY-MM-DD-HHmmss-default-{Smoke,Unit,Protocol,UI}.out.log` per Run A project, `YYYY-MM-DD-HHmmss-primary.out.log`, and `YYYY-MM-DD-HHmmss-full.out.log` beside the transcripts, plus `soak-{ui,protocol}-N.out.log` per soak iteration inside the stamp directory; triage reads the `.out.log` first, since the wrapper transcript carries only the script's own lines, trx plus gate logs under `build/nightly/YYYY-MM-DD-HHmmss/`, each leg transcript recording the suite scope plus the build-time HEAD at the top (captured once after the up-front build, so mid-run commits cannot misattribute legs). A same-day second run never overwrites the first run's evidence; only the morning report keeps its day-scoped name, always written by exactly the run that just finished. Archive rule (D00 T02 §15 PR5): every publication also lands a stamp-scoped archive (`morning-YYYY-MM-DD-HHmmss[-core].md`, immutable per publication) and `latest.txt` names the current stamp, so triage resolves the freshest run without globbing. A red leg never blocks the later legs: each leg runs, the report carries every red, and only the run's exit code is red. The task appends the §5 soak loop (UI plus Protocol x5) after the legs unless `-SkipSoak` is passed; the soak is flake hunting, the legs are the regression proof.

The morning report lands at `build/nightly/morning-YYYY-MM-DD.md`: date, HEAD, trigger, a per-leg table (test counts, gate verdict, infrastructure note, log path: no cell mixes verdict classes, D00 T02 §15 PR8), a separate enforcement verdict naming any non-quarantine skips, every failure with its filed finding ref (triage appends refs after filing each failure in the owning file, before the next section starts), a captures section (screenshot, window metadata, event slice, pre-kill dumps; dumps read n/a when the leg exited before capture), and uncollected debt as information with its cause. A Night debt section carries one entry per debt open at run start (collected counts with log, or uncollected with cause), and red Interactive collections stage finding stubs under Filings for triage to file. The current report is the worked example of the format.

Failure-capture policy (D00 T02 §22 item 1, D00-T02-S15-PR21): captures (screenshot, window metadata, event slice, pre-kill dumps) stay on this machine under ignored `build/nightly/<stamp>/captures-*` with the operator profile's access, and nothing that notifies (toast, poster, result JSON) ever attaches or quotes their bytes. Redaction: window metadata keeps a title only when the process is provably the run's own, a descendant of the governed run's PID (`Get-DescendantPids`, refusing a reused parent PID by creation time; a process whose parent already exited counts as foreign), and is a kind the run launches (`ScratchPad`, `testhost`, `ForegroundLog`, `JobControl`; shells and `dotnet` never qualify because the operator's own terminals run under those names); every other title, including an operator-opened ScratchPad, writes as `[title redacted]` (`Format-WindowRow`). Secret scanning: every `.txt`/`.log`/`.json` capture is scanned after it is written (`Protect-CaptureDir`, patterns in `$script:SecretPatterns`: GitHub, Anthropic, OpenAI, AWS, and Slack token shapes, private-key headers, bearer tokens, and assigned `password`/`secret`/`api-key`/`token` values in bare, quoted, and JSON forms); a hit replaces the whole file with a redaction note naming the patterns and adds a `SECRET-SCAN` note to the Captures section, so a partial mask is never trusted; a capture the scan cannot read or rewrite is deleted (fail closed), and one that cannot even be deleted raises a `SECRET-SCAN FAILED ... do not retain this run` note plus a `SECRET-SCAN-FAILED.txt` marker beside it. Retention enforces this rather than trusting notes: `NightlyRetention.ps1 -Retain` re-scans every text capture under the source's `captures-*` directories and refuses (`retain: PROTECTION REFUSED`, nothing copied) on a marker, a secret hit, or an unreadable capture (`Test-RetainableCaptures`). Size: a capture directory over 25 MB drops its screenshots with a size-cap note. Pre-kill dumps (`dumps-<leg>/<pid>.dmp`, written by `tools/JobControl` as `MiniDumpNormal`: thread stacks plus the module list, no heap, about 0.6 MB each) are binary, so they are never text-scanned; their control is the dump type (no heap, so managed document buffers and note text, which live on the heap, are not captured; stack frames can still hold fragments) plus locality and retention like every capture. Retention: captures follow the run evidence (30 days, `NightlyRetention.ps1 -Prune`); a retained run keeps its captures under the same checksums. Screenshots are not text-scanned (a default: OCR is out of scope; cost of changing: an OCR pass per capture); their control is locality plus retention, and the Interactive leg owns the foreground while it runs, so the primary screen shows the run, not the operator's work.

The Interactive leg is the night-debt collector (D00 T02 §10): at run start it snapshots open debt via `query night-debt`, resolves each debt id to its trait filter (a bare value means `Category=<value>`), and attributes the collection per debt; `-CollectDebt <id>` narrows the leg to one debt's filter, and with `-CheckOnly` it dry-runs the resolution with no side effects. Green collection appends `Night-collected:` (date, id, passed/failed/skipped, trx log path) after the debt's `Night-owed:` line for triage to commit, red collection stages finding stubs (test, first message line, test-file hint) under Filings and the debt stays open, and a zero-executed collection never closes debt (filter matched nothing: collector bug, run red). Stubs on safety or data-integrity shaped failures (data loss, corruption, integrity, disk, unauthorized, access denied, IO error) carry `REOPEN-CANDIDATE` for the agent to reopen through audit stance; the marker is a triage hint, never a decision.

Superset and census rules: only an exact-filter green run auto-appends `Night-collected:` with leg counts; a full-Interactive green run covering a narrower `&`-only Interactive debt closes with per-test subset counts from the trx when the filter is `FullyQualifiedName`/`Name`-attributable, else stages the evidence for triage to close with subset counts, `|`/`!` filters close on exact runs only, and collected totals must equal the debt's owed count (census mismatch reds as a collector bug and the debt stays open).

Closure-safe skips are quarantine-declared only: their proof transfers to the quarantine window, while capability or other skips hold the debt open with cause (no red: the leg stays green, the debt entry plus summary carry the cause); trx subsets close only fully executed (their skips carry no reason), and exact runs census passed plus failed plus quarantine skips against owed.

Abort rules: a leg that overruns its gate window is killed at the bell, fails the leg, and the run continues; legs without a gate window (Interactive, soak) are killed at the 1800s cap and fail the leg; a red build skips every leg but still writes its report; a dead run is resurrected by the guard cron at its next in-window fire, never re-driven by hand inside the window, and next-start recovery (§16) lands a RED record with the last-known phase plus evidence at the following run; a second invocation while one runs stands down on the mutex (exit 0, the holder owns the proof) and lands a uniquely-named loser report (`loser-<stamp>-pid<PID>.md`, `Status: stood-down`) without touching the holder's evidence; past the window, morning triage re-drives what the window allows (Run A plus Run B via `-SkipFenced -SkipSoak`; the Interactive collection waits for the next window). A locked box skips the Interactive leg with the skip logged and the run red (the box never locks per the §10 box facts, so a lock is an incident, not a debt cause).

Run deadline (D00 T02 §14): every leg starts only when its full cap plus 180 s kill slack fits inside the remaining run budget, so the all-hang catastrophe (13 legs × (caps + 180 s grace) = 24240 s worst case plus cleanup: 21900 s of caps plus 2340 s of kill grace) lands its report instead of dying by scheduler kill. Deadline math: `deadline = min(runStart + 4h, windowEnd) - 300s reserve`, start a leg only when `remaining >= cap + 180s`, where the window end (06:50 default, follows `SCRATCHPAD_INTERACTIVE_WINDOW`, crossing-midnight windows roll to tomorrow) binds in-window runs only (a manual daytime backup has no window boundary), the 300 s reserve covers reaping plus the atomic report, and the 180 s slack covers job-teardown latency on a kill (measured ~120 s; without it teardown leaks past the deadline); a run that starts with zero budget left fails fast (builds plus legs skipped, report lands immediately, whole run unproven); the build and the `-Smoke` path run outside the budget (fail-fast, nothing proves without a build). A leg whose cap no longer fits is budget-cut: skipped, marked unproven (never green) in the report's `Budget-cut` line plus its leg row, and the run reds. Core verdicts (the three regression-leg rows) publish to the fixed report path before soak starts, so a long night keeps its core proof; soak consumes only remaining budget, iteration by iteration, and the final report's `## Soak` ledger marks killed plus budget-cut iterations. Both publications carry a machine-checkable `Status:` line (`pre-soak core verdicts` vs `final`), so the guard plus triage distinguish them by content, never by presence alone. Verdict semantics: the overall run is RED when any leg is red, killed, or budget-cut; core regression status reads from the three leg rows, soak status from the `## Soak` ledger, whose fourth-phase verdict (GREEN with proved count, or RED naming failures plus unproven) fails the run like a leg. Killed or budget-cut soak iterations are infrastructure verdicts for morning triage, never quarantine inputs (quarantine triages test behavior, not deadline enforcement). Out-of-window manual backups run under the task limit alone (no window boundary); Interactive still skips outside the window, so no manual run executes foreground tests at an unsafe time. Cancellation (console Ctrl+C plus unhandled in-script errors) lands an atomic RED `Status: cancelled` record via the script trap; Stop-Job, scheduler stop, process kill, shutdown, and power loss cannot trap (proven: a stopped run lands nothing) and are covered by next-start recovery (filed §16). Simulation knobs (simulation only, warn loudly, never a governed proof): `SCRATCHPAD_RUN_DEADLINE_SECONDS` replaces the budget from run start (reserve bypassed), `SCRATCHPAD_LEG_CAP_SECONDS` replaces every leg cap. Either knob marks every report `(SIMULATION: not a governed proof)` and forces the run RED, so no sim output reads as governed proof. The up-front builds ride 600 s timed steps and the gate wait carries bell-plus-120 s grace measured from gate start (the bell runs concurrently with the suite; a fresh cap from receive time would double-charge the leg), so hung toolchains strand nothing either (the smoke path stays exempt: a manual diagnostic, never proof). Residual closed by §15 (`D00-T02-S14-R3-F2`): legs run out of process under JobControl job objects with kill-on-close plus pre-kill dumps, and teardown is bounded abandon-when-hung, so a wedged runspace strands no report.

Session matrix for the `InteractiveToken` task (D00 T02 §14 item 5; settings read live from `tools/tasks/nightly-ui.xml` plus `schtasks`): the task runs only on an interactive logon (`LogonType InteractiveToken`), daily 02:30, PT4H execution limit, `IgnoreNew` on overlap, `StartWhenAvailable`, `WakeToRun`. Locked desktop: the run starts (token held) but the Interactive leg skips as workstation-locked with the run red; Run A, Run B, and soak prove normally. Logged out: the run never starts (no token); `StartWhenAvailable` fires it at the next logon, and a still-unfired run is re-driven by hand as the manual backup. Sleeping: `WakeToRun` wakes the box for the 02:30 fire; if the wake fails, the run behaves as missed-start. Missed start (box off): `StartWhenAvailable` runs the task at next boot/logon inside the window, else the manual backup covers it. Reboot mid-run: the run dies with whatever evidence landed (core verdicts if past the legs); the guard cron resurrects at its next in-window fire, never by hand inside the window. (D00 T02 §16 item 5 proves or accepts each cell; see Session-matrix proofs.)

Run-evidence retention (D00 T02 §14 item 4): governed evidence lives under `build/nightly/retained/<run>/` (not ad-hoc scratch): each retained run carries its transcripts, trx plus gate logs, morning report, and a `SHA256SUMS` file over every evidence byte; retention is 30 days of nightly runs plus every run cited by a stamp (stamped runs never age out while their section stands). The 09-20 archives migrated under these rules (`nightly-rerun-2026-09-20`, `nightly-taskrun-2026-09-20`, checksummed). Retention is documented here (tracked) while the bytes stay under ignored `build/` (multi-MB binaries do not belong in git); each retained run also lands a tracked hash manifest under `docs/nightly-evidence/` (provenance plus SHA256 per file), so any copy of the bytes verifies against the record. Loss of retained evidence is an incident, loss of unretained scratch is not. Executable gates (D00 T02 §15, D00-T02-S14-PR15; owner DerickPayne): `tools/NightlyRetention.ps1 -Verify` checks every retained run's bytes against its SHA256SUMS plus the tracked manifest (missing bytes, mismatches, unlisted files, and manifest drift all fault); `-Prune` plans the deletion of stamp dirs plus loose stamp transcripts older than 30 days and deletes only with `-Execute`, stamp-cited runs carry `KEEP.txt` and are exempt, unknown shapes are skipped never auto-deleted; `-Retain -Source <stamp> -Name <run> -Provenance "..."` copies a run to `retained/` with SHA256SUMS plus manifest and KEEP-marks the source, refusing when free space falls below twice the source size and removing any partial target on copy, hash, or write failure. The scheduled shape is a weekly `-Verify` plus a weekly `-Prune -Execute` from the operator's maintenance window.

Retention quota and attended retain (D00 T02 §22 items 2 and 7): `-Retain` refuses loud (`retain: QUOTA REFUSED`, exit 1, nothing copied) when the KEEP-exempt set would pass its caps: 20 retained runs, 20 KEEP-marked stamp directories, and 2 GB across retained copies plus KEEP-marked sources (`-MaxRetained`, `-MaxRetainedBytes`; raising a cap is a command-line choice recorded with the retain). Retain is attended-only: the unattended nightly never retains and never writes a tracked file, so no night needs a commit; the retaining session commits the new `docs/nightly-evidence/<run>.md` manifest with the section that cites it. Every governed run proves both halves in its Run integrity section: `- Tree:` (the §16 start-and-end worktree fingerprint) and `- Catalog:` (a read-only `NightlyRetention.ps1 -Verify` over every retained run and manifest, `current (...)` or RED with the faults named, since loss of retained evidence is an incident).

Recovery and the run journal (D00 T02 §16 items 4, 12): every run journals its phase (`build/nightly/current.json`: stamp, pid, start, phase `started|core|final|cancelled`, atomic write) at launch, core publication, and final publication; the next start probes before writing its own journal, and a journaled run that is not the current run, never reached final, left no final archive, and owns no live process (PID-reuse guarded by start-time match) lands an atomic RED recovery record (`morning-<stamp>-recovery.md`: last-known phase, start, evidence, verdict) plus a `Recovered:` line in the new report, so a dead run surfaces exactly once with its phase named. A same-day supervisor tombstone at the fixed path links from the record as the same abandoned run instead of double-reporting the incident; a corrupt journal reads dead-unknown rather than silently passing. The path is proven by killed-run simulation (planted dead journal plus partial stamp dir: `nightly: recovered dead run 2026-09-20-020000 at phase legs`, record quoted, artifacts removed) and 52 fixture asserts (`tools/NightlyParse.Tests.ps1`). Scheduler health (D00 T02 §16 item 9): every run quotes four never-launched cases in its Run integrity section from a live unelevated COM read of the task: definition drift (live XML vs `tools/tasks/nightly-ui.xml` on triggers, action args, and time limit; provision owns repair), disabled task, expired credentials, and missing starts (no fire within 26 h of a daily task reads MISSING; never-fired reads bootstrap only while the registration is young; auth-shaped LastResult codes surface the credential residual post-fire). Run integrity and timer correlation (D00 T02 §16 items 7, 8, 10, 14): every report ends with a `## Run integrity` section quoting Launch (timer/demand-or-recovered/manual/unknown: scheduler-parented start within ±5 min of a defined daily trigger time with the scheduler's LastRunTime agreeing reads timer; anything else names its reason), Action (live task action plus invocation switches), Scheduler (the four health lines), Tree (start vs end content fingerprint: clean, stable, or MUTATED), Identity (consistency across stamp directories, archives, loser reports, incident ids, and the inherited latest.txt pointer, which the next run re-verifies as chain of custody), Timings (per-phase durations plus deadline reserve), per-phase duration lines against `tools/nightly-baseline.json` (warn is advisory, never red; gated legs compare test-seconds since the gate holds its window by design), Recovered, Omission, and Exit. Recurrence means two consecutive scheduled occurrences on unchanged reviewed code and configuration (no retries, demand starts, or mid-run edits); green means `Status: final` with no killed, cut, or unproven phases, full soak iterations, zero enforcement or infrastructure faults, and no filters, exclusions, quarantines, or population reductions past the reviewed set (D00 T02 §16 item 8: both timer reports quote these definitions holding). Durable evidence per run is the stamp archive plus fixed report, latest.txt pointer, 30-day plus stamp-cited retention with SHA256SUMS and tracked manifests, and checksum verification; the timer proofs quote this set for both runs.

Session-matrix proofs (D00 T02 §16 items 5, 13): locked is an accepted gap (owner operator; rationale: locking the daytime operator box to test is itself an interruption and the box never locks per §10 box facts; compensating control: the locked branch skips Interactive plus reds, logonui measured absent; expiry 2026-12-31; re-test trigger: any lock incident, which reds loudly by construction). Logged-out and missed-start configs are proven live (InteractiveToken plus StartWhenAvailable read from the live definition with drift:none quoted) while their behaviors are accepted gaps (owner operator; rationale: logout and power-off are untestable on the daytime operator box; compensating control: platform token semantics plus StartWhenAvailable plus the manual backup procedure, which leg-skipped runs prove executable; expiry 2026-12-31; re-test trigger: any logged-out morning or missed fire). Machine-readable results, notification, and trend (D00 T02 §17): every governed run publishes `morning-<stamp>.result.json` beside its stamp directory (schema version 1: stamp, day, identity, verdict, exit, trigger, launch, commit, per-leg ran plus counts plus gate plus killed plus cut plus test-seconds, soak ran plus verdict plus failed plus killed plus cut plus failures, quarantine windows plus overdue detail (test, due, owner), incidents, scheduler state, tree fingerprints, recovered line, timings, reserve, consumed, environment block, report path, note; `Test-ResultFile` validates identity plus version plus verdict plus verdict/exit consistency plus shaped legs (each with ran) plus a known soak verdict plus a present environment os (`unknown` is the honest value for unrecoverable nights, and it validates), and the emitter fails closed when its own file does not validate; timings may be legitimately empty for unproven legs, so presence is all the gate checks). The summary (`tools/NightlyTrend.ps1`, output `build/nightly/trend.md`, reading the current plus retained plus stood-down results, refreshed at every run end plus every stand-down plus every cancellation) renders one row per result (night, verdict, alert class, pass totals with pass rate, Run A/B test-seconds, soak verdict with failed names plus killed/cut counts, gate codes with `null` for ran-but-unproven, `skip` for legs that never ran (deliberately skipped or never started), and `-` for missing legs, reserve, quarantine overdue/due-soon counts with oldest age-at-night, soak-failure count, environment short form) with a flake-recurrence line naming incident ids seen on two or more nights, a Run A seconds median line, a current-quarantine line naming the oldest overdue age, a per-night budget ledger (all phase timings, budget used/left halves, RunA rank plus percentile in the rendered set), and a per-night environment ledger, so recurrence review is one read. Backfilled nights read environment unknown on every dimension (historical env is unrecoverable; the live box never stands in). `tools/NightlyBackfill.ps1 -RunDir <retained-run>` re-derives `result.json` for runs retired before the emitter (checksums plus tracked manifests extended for the new file, no re-run of tests); the 09-20 retained runs plus the fl5f1 red backfilled under this rule with retention verify green. The run toasts the morning under `Nightly <day> : <GREEN|RED> (<class>)` (counts, trigger, top incident, overdue quarantine with due plus owner, unacked REDs, report path, plus the fail-closed reason when the own result fails validation; best-effort, never reds the run) and routes the night to one alert class (test, gate, enforcement, infrastructure, degraded-soak, recovery, scheduler-no-start, by documented precedence) shared by the toast title and the trend row. A cancelled run toasts `CANCELLED` with its reason best-effort from the trap. A supervisor tombstone (hang or no-publish) lands a red `result.json` with unproven legs plus live environment, toasts, and refreshes the trend, so the supervised deadline RED demands acknowledgement like any other. Acknowledgement (D00 T02 §23, hardening §17 item 3): every RED or cancelled run identity is one demand, however many result copies carry it (retained copies and reruns dedupe; the demand key is run identity plus result checksum, and the checksum covers the schema version), and it stays on the unacked list in every later report and toast until a valid ack names it. A v2 ack is a committed `docs/nightly-acks/ack-<name>.md` whose leading `---` block carries `ack-version: 2`, one `run: <identity> sha256:<result checksum>` line per acknowledged run (a batch file names every run, so two same-day REDs need two run lines), `incidents:` listing exactly those runs' INC ids (or `none`), `owner`, `disposition` (`fixed`, `filed`, `quarantined`, `environment`, `expected`, or `duplicate`), `corrective-owner`, `due` (on or after `signed`), `finding` (a section ref whose `## N.` heading exists in its TODO file, an INC id from the runs or the incident ledger, or a commit that resolves; an invented link fails), and `signed`; prose length proves nothing and is never checked. The leading `---` block, not the file name, marks a v2 ack. The most recently written copy of a run's result is its current result, and an ack must name that checksum: a result rewritten after its ack reads STALE until re-acked, even while an older retained copy still carries the acknowledged bytes. An ack counts only once committed with no uncommitted edit (a history git cannot verify never counts), because its git history is the append-only integrity record (trunk never amends or force-pushes): the report's `## Acknowledgements` section quotes each ack's commits with author and date. An unacked RED is due 3 days after its day; past due it reads OVERDUE with an operator escalation and stages an `ack-overdue` finding stub under the section's staged filings, re-staged with the updated lateness each run until acknowledged (the run never writes a tracked file, so filing stays triage's commit). v1 day files (`ack-YYYY-MM-DD.md`, owner plus day plus substance) still acknowledge runs on or before the 2026-09-21 cutover and nothing after it.

Alert routing and delivery (D00 T02 §24): notification is part of the final publication only (the pre-soak core publication never notifies) and goes through `Invoke-NightlyNotify` in `tools/NightlyNotify.ps1`, keyed on run identity plus result checksum plus notification version (`$script:NotifyVersion`, separate from the result schema version) in `build/nightly/notify-ledger.json`, so a retried task, a supervisor recovery, or a rerun of the same result notifies once. Each class routes by a fixed table (owner, channel, severity, response SLA): `scheduler-no-start` operator, immediate, critical, 4 h; `infrastructure`, `recovery`, and `cancelled` operator, immediate, high, 8 h; `gate`, `enforcement`, and `test` triage (§9), digest, medium, 24 h; `degraded-soak` triage (§5), digest, low, 72 h; `green` digest, info; `stood-down` routes nowhere; an unknown class routes like `infrastructure`. Immediate sends retry twice; when every attempt fails the payload lands in `build/nightly/undelivered/` and every later report carries `- Delivery RED` until the morning reconciler re-sends it. Digest-channel results queue in `build/nightly/digest-queue.json`. The morning reconciler (`tools/NightlyMorning.ps1`, task `\ScratchPad\Nightly Morning` daily 07:05 from `tools/tasks/nightly-morning.xml`, registered by `tools/provision.ps1`; move the digest by editing that trigger and the provision spec together) runs independently of the nightly: it alerts `scheduler-no-start` once per missed date for every night in the last 7 days whose 06:50 window closed without a governed start (a timer- or demand-launched result that is neither simulated nor a stood-down loser, or a supervisor tombstone; manual runs never count), so a logon days later still reports the nights it slept through; it flushes the digest (every queued payload whole in its own `build/nightly/digest-<day>-<HHmmss>.md`, never overwriting an earlier flush, behind one summary toast that retries and falls back to the undelivered set); and it re-sends undelivered notifications with the read, send, and delete under the notify lock. `-DryRun` prints the plan and writes no notify state. One named mutex (`Local\ScratchPad.NightlyNotifyState`) serializes every read-modify-write of the ledger, the queue, and the undelivered set, and a writer that cannot take it fails loud. The toast title keeps the precedence class and the body lists every other outcome label (`Get-OutcomeLabels`), recovery notices (a canonical night GREEN after a RED canonical night, and every incident the §22 ledger closed), and launch evidence for the top incident. The body is capped at 7 lines by priority (0 fail-closed or report/result disagreement, 1 delivery or acknowledgement escalation, 2 top incident, 3 recovery, 4 overdue quarantine, 5 counts, 6 labels, 7 trigger), says `+N more in the report` when it truncates, and always ends with the report path: the stamp-scoped archive (`morning-<stamp>.md`, or `morning-<stamp>-cancelled.md` for a cancelled run), never the day file a later same-day run replaces. Undelivered fallbacks are named by run plus a hash of the whole key, so two failed notifications for different results of one run never overwrite each other. Before the exit line the run cross-checks the Markdown against the JSON field by field (`Test-ReportResultAgreement`: every leg row the result ran with its counts and a numeric gate code wherever the result recorded one, the incident set, soak verdict plus FAILED, killed, and budget-cut names both ways, the `- Budget:` consumed and reserve plus the Timings reserve, all eight `- Environment:` fields, and the exit line) and reds with the field named on any contradiction. Launch-related incidents (a §18 leak bundle or a failed launch record for the test that day) carry `bundle`, `screenshot`, and `launch-record` links in the Incident ledger section, the result's `incidentEvidence`, the toast, and the trend. The trend keeps one row per result but marks retries, simulations, and stood-down losers, and counts only canonical runs (per day the scheduler-launched run, else an on-demand task run, else the latest manual run) in the p50, the budget ranks, and flake recurrence. Delivery by session state: locked, the run starts (InteractiveToken) and the toast waits in Notification Center until unlock; asleep, WakeToRun wakes the box for the nightly and the reconciler runs at wake (StartWhenAvailable); rebooted, both tasks persist and StartWhenAvailable runs a missed trigger at the next logon; noninteractive (no desktop session, so the toast API fails), retries then the undelivered fallback, re-sent by the reconciler from the next interactive session and escalated in every report; logged out, an accepted gap: neither task can run without the user's token, so nothing delivers until the next logon, when the reconciler reports the missed night as `scheduler-no-start` (owner operator; rationale: InteractiveToken is required to drive the UI suite; compensating control: the logon-time reconciler plus the §16 missing-start check).

Incident identity and lifecycle (D00 T02 §22 items 3 and 6, D00-T02-S15-PR24, D00-T02-S17-PR26, D00-T02-S17-PR27): an incident id is `INC-` plus the first 8 hex of SHA-256 over the contract key `v2|<test>|<phase>|<failure class>|<HRESULTs>|<stack signature>` (`Get-IncidentKey` in `tools/NightlyParse.ps1`). Phase is the leg family (`run-a`, `run-b`, `interactive`, `ui-soak`, `protocol-soak`), so soak iterations of one suite merge. The failure class is the exception type or the failed xUnit assertion (`Assert.NotNull() Failure`), never the printed values; unknown shapes fall back to the first message line with decimal runs collapsed. HRESULTs (`0x` plus 8 hex, from message and stack) are kept verbatim, so `0x80131505` and `0x80004005` split. The stack signature is the top three frames outside `System.`, `Microsoft.`, and `Xunit.`, method names only, with compiler-generated ordinals collapsed, so a rebuild or a line move cannot split one failure. The same ids feed the §17 trend's flake recurrence, so the contract is shared; the fixture suite pins golden ids, and any normalization change that would move them fails there first. Contract v2 starts 2026-09-25: v1 ids (test plus digit-collapsed message) do not carry over, so recurrence restarts at that boundary. Lifecycle: the cross-night ledger `build/nightly/incidents.json` (ignored scratch, atomic write with read-back) creates each incident once, appends one occurrence per stamp on recurrence (idempotent per stamp), takes the owner from the quarantine list row when the test sits there (else keeps the recorded owner, else `unassigned`), and closes an open incident only on verified recovery: its test executed and passed in the same phase on 3 separate runs with no failure between (a failure resets the streak, a run that never executed the test neither counts nor resets; `Update-IncidentLedger -RecoveryRuns`), so a flake that passes most nights cannot close and reopen nightly. A closed incident seen again reopens with its history. The report's `## Incident ledger` section lists new, recurring, recovering, reopened, and closed incidents plus the open count; triage files a finding only for `new` lines under §9's file-every-failure rule, and `recurring` or `REOPENED` lines append to the finding already filed for that id, so no incident is ever filed twice. An unreadable or unwritable ledger reds the run rather than re-minting every incident.
