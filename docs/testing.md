# Testing

Unit, smoke, UI-automation, and protocol tests each have a harness under `tests/`, and one `dotnet test src/ScratchPad.slnx` run executes every suite (`src/Notepad.Neutral.slnf` filters the neutral scope for a fast check). The run includes the fenced interactive UI tests (below) plus the Category=Primary placement set, and each skips unless its safe context holds: the fenced set runs only inside the 02:00-06:50 window (or with SCRATCHPAD_INTERACTIVE_FORCE=1), owning the foreground while it runs, and the Primary set runs only under SCRATCHPAD_BACKGROUND=1 (or in the window/forced), so outside those contexts the run reads green-plus-skipped; the per-section gate is the default-filtered run, which never takes the foreground.

## Testing policy (operator decision 2026-10-14)

This section wins over every other rule on this page, and over `.claude/skills/process-todo-section/gates.md`, wherever they disagree. The app is already close to Windows 11 Notepad parity, and the scheduled runs and whole-suite gates took the operator's screen at night and during the day for no new information. So testing is scoped to what changed and never interrupts the operator.

- **No scheduled test runs.** The `\ScratchPad\Nightly UI`, `Nightly Foreground Single` and `Nightly Morning` tasks were removed on 2026-10-14, and `soak.yml` runs on `workflow_dispatch` only. `tools/provision.ps1 -Verify` faults if a task under `\ScratchPad\` or a schedule trigger in any workflow comes back. Never register a scheduled test task.
- **A section tests everything it implemented, and nothing else.** Its gate is a clean build, every test of the feature (the tests it added or changed plus the existing tests of the code it touched, one `--filter` over those classes, whatever their category), and `validate`. A red test of the feature holds the flip. The focus-free part runs with `-e SCRATCHPAD_BACKGROUND=1`. A section gate never runs the whole UI suite and needs no ForegroundLog proof (run it only when the section changes focus or window placement).
- **Every section gate also runs every golden comparison** (`Visual=Golden`, focus-free, about a minute), so a visual regression in a screen the section never touched fails the same day. `GoldenInventoryTests` keeps the set honest: each committed `resources/baseline/app/*.png` (except `*-evidence.png` crops) has a `UiGolden.AssertMatches` test, each such test is tagged, and none is fenced.
- **The feature's own Interactive and Primary tests run in its gate too**, scoped by the same filter, so they take the screen for seconds, not hours: Primary with `-e SCRATCHPAD_BACKGROUND=1`, Interactive with `-e SCRATCHPAD_INTERACTIVE_FORCE=1` (the operator accepted this scoped interruption on 2026-10-14). Every forced fenced run (`SCRATCHPAD_INTERACTIVE_FORCE=1`: the gate's step and the operator's phase-close run) first waits for the operator to leave the keyboard and mouse alone for `SCRATCHPAD_IDLE_SECONDS` (default 60) and skips as `Operator active` after `SCRATCHPAD_IDLE_MAX_WAIT_SECONDS` (default 900); `UiOperatorIdle` owns the gate, once per test host at discovery. Unforced runs, listing, and child test runs never wait. A feature the user sees is also checked visually in its gate: the session captures it in the built app (the feature's UI test saves a `UiCapture.PrintCapture` frame from a fresh seeded profile; `tools/CaptureBaseline stub` serves fresh-launch frames), looks at it beside the stock Notepad capture in `resources/baseline/stock/`, and records the verdict and capture paths in the commit (`.claude/skills/process-todo-section/gates.md` step 4); an unintended difference is a red gate. A capture whose differences are all intended or recorded with an owner (`docs/parity-review.md`) is committed as a golden under `resources/baseline/app/` after three stable runs, which turns the one-off check into a permanent regression test (`UiGolden`); menus and in-window dialogs stay by-eye checks until D06 T01 §7 pins WinUI's input mode. Prefer focus-free UIA tests when writing a feature's tests; a physical key, drag, or cursor test is the exception. Only when the host cannot run them (locked session, no display) does the section say so in its `Verified:` evidence; the operator's foreground legs at close cover them.
- **The full suite runs when a phase, a TODO file or a release closes, never on a timer.** The closing session runs the focus-free full suite itself: `dotnet test src/ScratchPad.slnx --filter "Category!=Interactive&Category!=Primary" -e SCRATCHPAD_BACKGROUND=1`. The foreground legs (Primary and Interactive) take the screen, so only the operator starts them, when convenient (Foreground legs at close, below). Until then they stay owed; the close does not wait for them.
- **Quarantine has no deadline.** A quarantined test stays quarantined until its owning section fixes or removes it; overdue quarantine due dates no longer fail anything.
- Retired with this policy (each carries a `Moved:` marker pointing here): D00 T09 §1-8 (nightly operator control), D00 T02 §16 (timer-fired run verification), D00 T11 §2 (night-debt governance residuals), D00 T13 §1-2 (CI soak population). The flaky-test fixes (D01 T01 §35, D01 T02 §16, D06 T01 §6) stay open as product work.
- Retired 2026-10-18 with the process simplification: the nightly runner and its ledgers (Foreground legs at close, below).

## Framework

xUnit v2 with the VSTest runner: `Microsoft.NET.Test.Sdk` 17.14.1, `xunit` 2.9.3, `xunit.runner.visualstudio` 2.8.2, pinned per project with lockfiles. Every test project targets `net10.0` and references only neutral libraries, keeping the suites OS-independent; Windows-only coverage comes from the UI suite driving the real binary.

xUnit v3 with the Microsoft Testing Platform runner was evaluated twice and ships nowhere: T01 §5 proved zero-test discovery on our project and xUnit's own template across many configurations, and the T02 §1 re-evaluation reproduced it on the current vendor `xunit3` template (`xunit.v3.mtp-v2` 4.0.1) retargeted to `net10.0`, where a real `[Fact]` reports `Zero tests ran` with exit code 5. Re-evaluate only when a new v3 or template release claims the discovery path fixed.

## Suites

`tests/Smoke/` holds the one wiring test that proves the harness works; `tests/Unit/` holds unit tests over the neutral libraries, starting with the framework-choice tests. `tests/UI/` drives the stub window under FlaUI (launch, title assert, close, with a failure screenshot); the ACP loopback fixture (T02 §4) arrives with its section. Test-only helpers shared between suites live under `tests/Common/` per its README.

## Commands

Run everything for the host OS with the `dotnet test` commands above. Run one suite with `dotnet test tests/Unit` (or `tests/Smoke`, `tests/UI`). Filter within a run with `--filter`, for example `dotnet test <solution> --filter Smoke`. Test output uses the default console logger; anything written under `TestResults/` is gitignored.

## UI suite preconditions

The UI suite drives real windows and native dialogs, so two machine settings must match the golden-capture environment: dark app theme (`AppsUseLightTheme` 0, else goldens mismatch) and visible file extensions (`HideFileExt` 0, else dialog prefill reads, file-list names, and save routing shift and 6 MenuBarTests fail). Verify with `(Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Themes\Personalize').AppsUseLightTheme` and `(Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Advanced').HideFileExt`. (CI set both before its test step until 2026-09-17, when UI tests left CI; the settings still gate local runs.)

## Uninterrupted gate (D00 T02 §8)

Default run, background-safe: `dotnet test tests/UI --filter "Category!=Interactive&Category!=Primary" -e SCRATCHPAD_BACKGROUND=1`. The `-e` flag is load-bearing: it is the only channel that reaches the app through the test host (shell exports do not propagate, measured 2026-09-17), and it makes every window start minimized. The suite then moves each window to the secondary monitor (off-screen on single-monitor boxes) and drives it through UIA patterns: visible there but never activated, so no foreground and no cursor. Fenced run, visibly on demand: `dotnet test tests/UI --filter "Category=Interactive"` with no `-e` flag. Fenced tests own the foreground and the cursor (physical keys, drags, dialog clicks), so run them when the interruption is yours to spend. Placement run, focus-free on the primary: `dotnet test tests/UI --filter "Category=Primary" -e SCRATCHPAD_BACKGROUND=1` with the foreground log under `--expect-primary`; its windows show where the app put them (geometry and cascade premises) without ever activating.

Foreground proof rides alongside the default run: `Bin/ForegroundLog/Debug/ForegroundLog.exe <seconds> <logpath>` polls the foreground window and exits 1 naming the run red if ScratchPad ever held it. Green means the default suite passed with zero failures AND the log flagged zero foreground holds; a passing suite with a flagged log is a gate failure (some test activated a window). The same run records a census of app windows and a placement-event log, and the gate fails on a primary birth or a primary rest. The exact recording and agreement rules (which windows and events each stream records, popup and minimized-window handling, hook-loss tolerance, and where the two streams must agree) are specified in `tools/ForegroundLog/Program.cs` (its header comment plus the comment at each rule), which is authoritative and maintained beside the code; this page does not restate them (operator decision 2026-10-03, D00 T06 §2). The fenced set is green when it passes visibly, and the placement set is green when it passes with its census on primary and the event log agrees the birth was on primary. The input audit behind the split lives in `docs/ui-input-audit.md`.

Quiet hours hard-gate the fenced set: every `Category=Interactive` test runs under `[InteractiveFact]` (or `[HookFact]`, which composes the same gate with a hook-availability probe), which reports Skipped outside the foreground window (02:00-06:50 local, operator schedule 2026-09-17), so even an unfiltered daytime run cannot interrupt. `SCRATCHPAD_INTERACTIVE_WINDOW` (`HH:mm-HH:mm`) moves the window and `SCRATCHPAD_INTERACTIVE_FORCE=1` runs regardless for an explicitly accepted interruption; unparseable config fails closed to skip. Reflection guards pin the pairing both directions (`QuietHoursTests.EveryGatedTestCarriesTheInteractiveTrait` plus `EveryInteractiveTraitCarriesAGate`). A daytime full-solution run reads green-plus-skipped, never fully proven; only the operator's forced run at close (Foreground legs at close, below) executes the fenced set outside the window.

Background births and the sibling sweep (D00 T02 §18, §26, §34): a window born under `SCRATCHPAD_BACKGROUND=1` parks the helper windows its construction created at the off-screen target, and `Notepad.Core.SiblingSelection` decides from a snapshot taken when the construction began: preexisting windows, windows another main owns, windows an app worker thread created (the print thread registers itself), and mains are skipped, and a sweep without a fresh snapshot pins nothing. WinUI creates its top-level helpers once per UI thread, some on its own framework threads, so the first window's birth is where helpers pin and later births pin none. Under the test-run marker (`SCRATCHPAD_TEST_RUN=1`) with `SCRATCHPAD_SWEEP_LOG` naming a file, each sweep appends `sweep main=0x.. target=x,y pinned=0x..@x,y skipped=0x..(reason)`, the pinned positions read back right after each pin, so the UI suite proves the decision directly (`LaunchTests.SweepLogScope`) instead of inferring it from WinEvents.

Sibling sweep second residuals (D00 T02 §41): the construction snapshot is a field initializer, so it runs before the base `Window` constructor and helpers the framework creates there are this birth's (the hold proof `FirstBirthPreexistingSetMatchesAnOutsideObservation` failed on the old constructor-body snapshot, naming a base-constructor helper read as preexisting). Every window the snapshot sees carries a `ScratchPad.SiblingMark` property with the snapshot's generation, so a handle value reused by a new window reads new, and a window that refused the mark reads `ambiguous` (skipped and reported, never pinned blind), as does a window whose owner or thread cannot be read. Each sweep claims its main and the helpers it pinned and stamps each with a `ScratchPad.SiblingClaim` property; any other construction reads a claimed window as `other-construction`, whatever the order of the sweeps, but only while the window still carries that claim's mark, so a claimed handle reused by a new window is not misattributed. Revalidation compares thread, class, and both marks; an exact handle value reused on the same thread with the same class and no marks is outside what Win32 exposes (HWND values carry a reuse counter in their high word). Delayed passes are kept per main, so a second construction never drops the first one's, and the barrier waits for each born main's `sweep-late` line (the app's record that its last posted placement ran) before draining. The delayed pass keeps each decided window's identity (thread and class), so a handle reused since the sweep is decided again; the launch record waits, bounded, for the delayed pass's `sweep-late` line and names it missing when it has not logged (that per-launch log is kept and pruned after a day); the guard reads a namespace-alias qualifier (`I::DllImport`) and `global::` like a dotted name. Each selected window is read again just before its move, and a destroyed, reused, or re-owned handle is skipped (`gone-before-move`, `reused-before-move`, `reowned-before-move`). A delayed pass runs on the first UI-thread idle after the show and pins helpers born after the sweep (`sweep-late` lines with the same generation); it does nothing when another construction began since (`late-skipped-overlap`), and helpers born after it are runtime popups, owned separately (the documented bound). Sweep-log lines now read `<phase> main=0x.. target=x,y gen=N pinned=.. skipped=..`. Test seams (run marker required): `SCRATCHPAD_TEST_LATE_HELPER=1` plants one hidden popup after the sweep, and `SCRATCHPAD_TEST_HOLD=<name>` holds the app before its first window (`<name>-held`, `<name>-release`, 30 s bound). The location recorder drains to an observation barrier (a synchronous `WM_NULL` to each app window, then a barrier message behind the pending events) and the proofs print `recorder drained N event(s) at the barrier`. Every UI launch arms a sweep log, and launch records (schema `launch-diagnostics/2`) quote the birth's sweep lines in `sweep`. The launch guard states its threat model in `tests/UI/LaunchGuard.cs`: it enforces launcher calls in any source shape, reflection through its member choke points, and P/Invoke declarations in every spelling (DllImport or LibraryImport, suffixed, qualified, aliased); runtime-resolved native exports, runtime-compiled code, and launches outside `tests/UI` are outside it, pinned by `ShapesOutsideTheStatedBoundaryAreNotClaimed`.

## Birth rule (D00 T02 §11)

Backgrounded launches birth off-screen: `UiLaunch.SeedSettings` seeds an origin derived outside the virtual screen whenever `SCRATCHPAD_BACKGROUND=1` and the caller left geometry at the 50/50 defaults (derivation D00 T02 §18: `UiLaunch.DeriveOffScreenOrigin` reads SM_XVIRTUALSCREEN, SM_YVIRTUALSCREEN, SM_CXVIRTUALSCREEN, and SM_CYVIRTUALSCREEN in physical pixels and places the window a full window-width past the right edge, falling back to flush with that edge and then the same pair above, to the left, and below, skipping any side whose coordinate overflows; never a fixed point, which a very wide topology can contain), so the first window restores where no census line can call it primary and no birth flash ever paints on the primary. ForegroundLog's census and placement-event log then check for primary births and rests under the rules specified in `tools/ForegroundLog/Program.cs` (see the foreground proof above). Explicit geometry wins: any X/Y the caller set survives seeding, which is how the Primary set keeps its on-primary premises (every Primary test seeds an explicit on-primary rect); the one exception is an explicit seed equal to the 50/50 defaults, which the store cannot tell from untouched geometry, so it maps off-screen too (`SeedPrecedenceTests.ExplicitDefaultValuedGeometrySeedsOffScreen`, D00 T02 §18). All five launch helpers (`LaunchApp`, `LaunchAppWithArgs`, `SeedSettings`, `SeedSettingsFile`, `AppExePath`) live in `tests/UI/UiLaunch.cs` only; per-file copies are removed, not wrapped. `SeedSettingsFile` is the path-returning seed for callers that own their own cleanup; it applies the same background rule. Unseeded paths birth off-screen too: under `SCRATCHPAD_BACKGROUND=1` the app maps an untouched 50/50 default to an off-screen origin itself (`MainWindow.BirthOrigin` through `PinBirthBeforeShow`, D00 T02 §18), so redirect-created windows and direct launches pin off-screen before their show, and only an explicit on-screen seed keeps the stock cascade. The funnel (`UiForeground.Background`) stays as the safety net before driving: `UiForeground.PlaceForBackground` sets the placement on the suite display before a no-activate show and then settles (placement lands before the show, D00 T02 §18).

## Fence-with-proof rule (D00 T02 §8 item 12)

A test is fenced only with a quoted background-fail plus foreground-pass pair: run it backgrounded (the default run with `-e SCRATCHPAD_BACKGROUND=1`) and quote the failure, run it foreground and quote the pass, and cite both in a `// Fenced:` comment on the test. A fence without its pair is a guess, not a gate. The 28 fences shipped with §8 predate the rule and carry grandfather notes citing the audit (`docs/ui-input-audit.md`) section or mechanism instead; a grandfathered fence that is ever un-fenced and re-fenced owes the pair like any new fence. Two placement-premise tests (geometry restore, cascade) moved to the `Category=Primary` set with cited pairs instead of fences under the item 7 revision.

Interruption-risk exception (D00 T02 §21 item 1): a test whose physical press passes backgrounded still stays fenced when the press itself takes the operator's foreground (a physical key needs focus, so `UiInput.Press` activates the window and would steal it from whoever is typing). Its pair is the backgrounded-forced pass plus the foreground pass, and its `// Fenced:` comment cites this exception by name instead of a background failure. Today it covers `AcceleratorTests.ChordCtrlShiftGOpensStats`, `ChordCtrlShiftHOpensSnapshots`, and `ChordCtrlShiftXOpensExport`. The exception never admits a test that could run through UIA patterns instead: only a test whose point is the physical press qualifies.

## Foreground legs at close

The Primary and Interactive legs take the screen, so only the operator starts them, when a phase, a TODO file or a release closes (the focus-free leg already ran in the closing session):

```powershell
dotnet test tests/UI --filter "Category=Primary" -e SCRATCHPAD_BACKGROUND=1
dotnet test tests/UI --filter "Category=Interactive" -e SCRATCHPAD_INTERACTIVE_FORCE=1
```

The forced Interactive run first waits for operator idle (`UiOperatorIdle`, above). A red test becomes a TODO item through `add-todo`. The nightly runner, its scheduled tasks, ledgers and night-debt collection were removed on 2026-10-18 (`docs/specs/2026-10-18-simplify-process-design.md`); they are recoverable from the `pre-simplify` tag.

## Population fingerprint and build evidence

`tests/UI/TestPopulation.fingerprint` (schema `population/3`) records each leg's member methods, method and case counts, and a hash plus rows of each leg's case display names, so a dropped, renamed, re-traited or swapped test drifts even at an equal count. The Windows CI job runs `tools/Test-TestPopulation.ps1` after the build (step `Check test population fingerprint`): it prints `population OK run-a=M/C run-b=M/C interactive=M/C`, or the drift lines and exit 1 (exit 2 when the build, the fingerprint or discovery cannot be read). After any change that adds, removes, renames or re-traits a UI test, build, regenerate with `tools/Update-TestFingerprint.ps1`, and review the diff. Excluded cases are listed in `docs/test-exclusions.md`.

Discovery runs inside `Invoke-WithForcedDiscovery`, which sets `SCRATCHPAD_INTERACTIVE_FORCE=1` and `SCRATCHPAD_DISCOVERY_LISTING=1` and restores both, so a fenced or capability-gated Theory lists all its rows at any hour (`GatedTheoryAttribute`, `DiscoveryListingTests`). Cases whose display names xunit cuts are identified by `tools/CaseIdentity` from the built assembly's data values.

Freshness is by content: every UI build writes `Bin/UI/Debug/build-inputs.digest` and `build-binding.txt` (`tools/Write-BuildInputsDigest.ps1`, run by `tests/UI/UI.csproj`), and every `src` project writes compile evidence beside its assembly (`tools/Write-CompileEvidence.ps1`, run by `Directory.Build.targets`). The digest covers each build input (`Get-UiBuildInputs`: sources, XAML, project files, imports, linked items, shared build files), the restore result and the SDK version; the population check and the regen refuse a stale build by naming the first differing input, and the refusal names `dotnet build src/ScratchPad.slnx --no-incremental`. The functions live in `tools/TestBuild.ps1`; `tools/BuildInputsDigest.Tests.ps1` is their fixture suite.

## Gate attribution and the sibling sweep

Gate process attribution (D00 T02 §49): the foreground gate attributes every event and census window to its process by (pid, process start time), resolved when the event arrives, never from a run-long pid cache, so a pid a ScratchPad test process held and another process reused later reads as that other process; each EVENT and CENSUS line names `exe=` (the full executable path, `%` and spaces percent-encoded) and `started=` for the process it counted; a process whose start time cannot be read is never cached, so each of its events is resolved afresh. `ForegroundLog selftest` runs the attribution fixtures (a reused pid never counts against the app; an event line names its executable), and `GateAttributionTests` runs it in Run A.

Sibling sweep third residuals (D00 T02 §48): an overlapped birth (another construction began before its delayed pass) never pins blind and never drops a helper silently: a window the pass would have pinned reads `overlap-unplaced`; every sweep and delayed-pass line ends with a placement `verdict=`, which fails naming each visible window left `ambiguous` or `overlap-unplaced` (`SiblingSelection.PlacementVerdict`); claim attribution holds both ways on a shared framework thread; the location recorder states its delivery guarantee (an event is observed only once `DrainToBarrier` returns, and each rect is read at delivery), fails the proof on overflow (a capacity bound, 4096 by default), and carries a planted move-and-snap-back control (`LocationRecorderSeesAPlantedMoveAndFailsOnOverflow`); the first-birth proof requires every window born during the construction, observed from outside, to be named by the sweep or its delayed pass (`FirstBirthGaps`), each pinned helper to read back at the target, and the verdict to pass; a construction that throws before its sweep abandons its pending snapshot (`SiblingSnapshotSlot.Abandon`, called by the window factory); launch records add `generation` and `sweepOutcome` (complete, late-missing, log-missing, truncated, or none) from their own lines only; the delayed pass recomputes a target a monitor attached since would show (`SiblingSelection.Retarget`, logged as `retarget`); and twenty births and teardowns keep the claim table within the live windows and each decision under 50 ms.

## Golden captures

`resources/baseline/` holds stock Notepad reference captures plus goldens of our own surfaces at canonical size; `tests/UI` compares fresh captures against them under the committed `tolerance.json` policy. Captures come from `tools/CaptureBaseline`; the refresh procedure in `resources/baseline/README.md` governs re-capturing after intentional changes.

## Quarantine

Flaky tests are quarantined by procedure (`docs/soak-and-quarantine.md`, T02 §5), never deleted or silently skipped. CI telemetry and VM-based runs were retired on 2026-09-14; UI tests left CI on 2026-09-17 (CI gates build plus launch smoke only), so all suites run locally on the dev box, with the UI suite driving the real binary on the interactive session.
