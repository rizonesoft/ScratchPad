# Testing

Unit, smoke, UI-automation, and protocol tests each have a harness under `tests/`, and one `dotnet test src/ScratchPad.slnx` run executes every suite (`src/Notepad.Neutral.slnf` filters the neutral scope for a fast check). The run includes the fenced interactive UI tests (below) plus the Category=Primary placement set, and each skips unless its safe context holds: the fenced set runs only inside the 02:00-06:50 window (or with SCRATCHPAD_INTERACTIVE_FORCE=1), owning the foreground while it runs, and the Primary set runs only under SCRATCHPAD_BACKGROUND=1 (or in the window/forced), so outside those contexts the run reads green-plus-skipped; the per-section gate is the default-filtered run, which never takes the foreground.

## Framework

xUnit v2 with the VSTest runner: `Microsoft.NET.Test.Sdk` 17.14.1, `xunit` 2.9.3, `xunit.runner.visualstudio` 2.8.2, pinned per project with lockfiles. Every test project targets `net10.0` and references only neutral libraries, keeping the suites OS-independent; Windows-only coverage comes from the UI suite driving the real binary.

xUnit v3 with the Microsoft Testing Platform runner was evaluated twice and ships nowhere: T01 §5 proved zero-test discovery on our project and xUnit's own template across many configurations, and the T02 §1 re-evaluation reproduced it on the current vendor `xunit3` template (`xunit.v3.mtp-v2` 4.0.1) retargeted to `net10.0`, where a real `[Fact]` reports `Zero tests ran` with exit code 5. Re-evaluate only when a new v3 or template release claims the discovery path fixed.

## Suites

`tests/Smoke/` holds the one wiring test that proves the harness works; `tests/Unit/` holds unit tests over the neutral libraries, starting with the framework-choice tests. `tests/UI/` drives the stub window under FlaUI (launch, title assert, close, with a failure screenshot); the ACP loopback fixture (T02 §4) arrives with its section. Test-only helpers shared between suites live under `tests/Common/` per its README.

## Commands

Run everything for the host OS with the `dotnet test` commands above. Run one suite with `dotnet test tests/Unit` (or `tests/Smoke`, `tests/UI`). Filter within a run with `--filter`, for example `dotnet test <solution> --filter Smoke`. Test output uses the default console logger; anything written under `TestResults/` is gitignored.

## UI suite preconditions

The UI suite drives real windows and native dialogs, so two machine settings must match the golden-capture environment: dark app theme (`AppsUseLightTheme` 0, else goldens mismatch) and visible file extensions (`HideFileExt` 0, else dialog prefill reads, file-list names, and save routing shift and 6 MenuBarTests fail). Verify with `(Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Themes\Personalize').AppsUseLightTheme` and `(Get-ItemProperty 'HKCU:\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\Advanced').HideFileExt`. (CI set both before its test step until 2026-09-17, when UI tests left CI; the settings still gate local runs.)

## Uninterrupted gate (D00 T02 §8)

Default run, background-safe: `dotnet test tests/UI --filter "Category!=Interactive&Category!=Primary" -e SCRATCHPAD_BACKGROUND=1`. The `-e` flag is load-bearing: it is the only channel that reaches the app through the test host (shell exports do not propagate, measured 2026-09-17), and it makes every window start minimized. The suite then moves each window to the secondary monitor (off-screen on single-monitor boxes) and drives it through UIA patterns: visible there but never activated, so no foreground and no cursor. Fenced run, visibly on demand: `dotnet test tests/UI --filter "Category=Interactive"` with no `-e` flag. Fenced tests own the foreground and the cursor (physical keys, drags, dialog clicks), so run them when the interruption is yours to spend. Placement run, focus-free on the primary: `dotnet test tests/UI --filter "Category=Primary" -e SCRATCHPAD_BACKGROUND=1` with the foreground log under `--expect-primary`; its windows show where the app put them (geometry and cascade premises) without ever activating.

Foreground proof rides alongside the default run: `Bin/ForegroundLog/Debug/ForegroundLog.exe <seconds> <logpath>` polls the foreground window and exits 1 naming the run red if ScratchPad ever held it. Green means the default suite passed with zero failures AND the log flagged zero foreground holds; a passing suite with a flagged log is a gate failure (some test activated a window). The same run records a census of every app HWND (monitor, rect, iconic state) and a placement-event log of each window's first visible bounds (EVENT lines from show and location events). It fails when any window rests on the primary monitor or when a primary birth shows up in the event log; iconic, invisible, and zero-area windows are recorded but excluded. Placement is by rect intersection (off-screen reads offscreen, never primary). Resting still means seen twice on the census. The event log records the birth even when that flash never spans two polls, and the gate is green only when every placed census window has an event and the two reports agree on zero primary births. A window may rest on the secondary monitor after an off-screen birth; that still agrees. Primary on only one side does not. The fenced set is green when it passes visibly, and the placement set is green when it passes with its census on primary and the event log agrees the birth was on primary. The input audit behind the split lives in `docs/ui-input-audit.md`.

Quiet hours hard-gate the fenced set: every `Category=Interactive` test runs under `[InteractiveFact]` (or `[HookFact]`, which composes the same gate with a hook-availability probe), which reports Skipped outside the foreground window (02:00-06:50 local, operator schedule 2026-09-17), so even an unfiltered daytime run cannot interrupt. `SCRATCHPAD_INTERACTIVE_WINDOW` (`HH:mm-HH:mm`) moves the window and `SCRATCHPAD_INTERACTIVE_FORCE=1` runs regardless for an explicitly accepted interruption; unparseable config fails closed to skip. Reflection guards pin the pairing both directions (`QuietHoursTests.EveryGatedTestCarriesTheInteractiveTrait` plus `EveryInteractiveTraitCarriesAGate`). A daytime full-solution run reads green-plus-skipped, never fully proven; only the nighttime run executes the fenced set.

Background births and the sibling sweep (D00 T02 §18, §26, §34): a window born under `SCRATCHPAD_BACKGROUND=1` parks the helper windows its construction created at the off-screen target, and `Notepad.Core.SiblingSelection` decides from a snapshot taken when the construction began: preexisting windows, windows another main owns, windows an app worker thread created (the print thread registers itself), and mains are skipped, and a sweep without a fresh snapshot pins nothing. WinUI creates its top-level helpers once per UI thread, some on its own framework threads, so the first window's birth is where helpers pin and later births pin none. Under the test-run marker (`SCRATCHPAD_TEST_RUN=1`) with `SCRATCHPAD_SWEEP_LOG` naming a file, each sweep appends `sweep main=0x.. target=x,y pinned=0x..@x,y skipped=0x..(reason)`, the pinned positions read back right after each pin, so the UI suite proves the decision directly (`LaunchTests.SweepLogScope`) instead of inferring it from WinEvents.

Sibling sweep second residuals (D00 T02 §41): the construction snapshot is a field initializer, so it runs before the base `Window` constructor and helpers the framework creates there are this birth's (the hold proof `FirstBirthPreexistingSetMatchesAnOutsideObservation` failed on the old constructor-body snapshot, naming a base-constructor helper read as preexisting). Every window the snapshot sees carries a `ScratchPad.SiblingMark` property with the snapshot's generation, so a handle value reused by a new window reads new, and a window that refused the mark reads `ambiguous` (skipped and reported, never pinned blind), as does a window whose owner or thread cannot be read. Each sweep claims its main and the helpers it pinned and stamps each with a `ScratchPad.SiblingClaim` property; any other construction reads a claimed window as `other-construction`, whatever the order of the sweeps, but only while the window still carries that claim's mark, so a claimed handle reused by a new window is not misattributed. Revalidation compares thread, class, and both marks; an exact handle value reused on the same thread with the same class and no marks is outside what Win32 exposes (HWND values carry a reuse counter in their high word). Delayed passes are kept per main, so a second construction never drops the first one's, and the barrier waits for each born main's `sweep-late` line (the app's record that its last posted placement ran) before draining. The delayed pass keeps each decided window's identity (thread and class), so a handle reused since the sweep is decided again; the launch record waits, bounded, for the delayed pass's `sweep-late` line and names it missing when it has not logged (that per-launch log is kept and pruned after a day); the guard reads a namespace-alias qualifier (`I::DllImport`) and `global::` like a dotted name. Each selected window is read again just before its move, and a destroyed, reused, or re-owned handle is skipped (`gone-before-move`, `reused-before-move`, `reowned-before-move`). A delayed pass runs on the first UI-thread idle after the show and pins helpers born after the sweep (`sweep-late` lines with the same generation); it does nothing when another construction began since (`late-skipped-overlap`), and helpers born after it are runtime popups, owned separately (the documented bound). Sweep-log lines now read `<phase> main=0x.. target=x,y gen=N pinned=.. skipped=..`. Test seams (run marker required): `SCRATCHPAD_TEST_LATE_HELPER=1` plants one hidden popup after the sweep, and `SCRATCHPAD_TEST_HOLD=<name>` holds the app before its first window (`<name>-held`, `<name>-release`, 30 s bound). The location recorder drains to an observation barrier (a synchronous `WM_NULL` to each app window, then a barrier message behind the pending events) and the proofs print `recorder drained N event(s) at the barrier`. Every UI launch arms a sweep log, and launch records (schema `launch-diagnostics/2`) quote the birth's sweep lines in `sweep`. The launch guard states its threat model in `tests/UI/LaunchGuard.cs`: it enforces launcher calls in any source shape, reflection through its member choke points, and P/Invoke declarations in every spelling (DllImport or LibraryImport, suffixed, qualified, aliased); runtime-resolved native exports, runtime-compiled code, and launches outside `tests/UI` are outside it, pinned by `ShapesOutsideTheStatedBoundaryAreNotClaimed`.

## Birth rule (D00 T02 §11)

Backgrounded launches birth off-screen: `UiLaunch.SeedSettings` seeds X/Y 10000 whenever `SCRATCHPAD_BACKGROUND=1` and the caller left geometry at the 50/50 defaults, so the first window restores where no census line can call it primary and no birth flash ever paints on the primary. ForegroundLog writes one EVENT line per window at the first visible show or location event, and the gate requires that line's monitor class to match the census. Explicit geometry always wins: any X/Y the caller set survives seeding, which is how the Primary set keeps its on-primary premises (both Primary tests seed explicit rects). All five launch helpers (`LaunchApp`, `LaunchAppWithArgs`, `SeedSettings`, `SeedSettingsFile`, `AppExePath`) live in `tests/UI/UiLaunch.cs` only; per-file copies are removed, not wrapped. `SeedSettingsFile` is the path-returning seed for callers that own their own cleanup; it applies the same background rule. The funnel (`UiForeground.Background`) stays as the safety net for unseeded paths: redirect-created windows and direct launches still birth at the cascade, so show-then-move with sleep-after-move keeps covering them.

## Fence-with-proof rule (D00 T02 §8 item 12)

A test is fenced only with a quoted background-fail plus foreground-pass pair: run it backgrounded (the default run with `-e SCRATCHPAD_BACKGROUND=1`) and quote the failure, run it foreground and quote the pass, and cite both in a `// Fenced:` comment on the test. A fence without its pair is a guess, not a gate. The 28 fences shipped with §8 predate the rule and carry grandfather notes citing the audit (`docs/ui-input-audit.md`) section or mechanism instead; a grandfathered fence that is ever un-fenced and re-fenced owes the pair like any new fence. Two placement-premise tests (geometry restore, cascade) moved to the `Category=Primary` set with cited pairs instead of fences under the item 7 revision.

Interruption-risk exception (D00 T02 §21 item 1): a test whose physical press passes backgrounded still stays fenced when the press itself takes the operator's foreground (a physical key needs focus, so `UiInput.Press` activates the window and would steal it from whoever is typing). Its pair is the backgrounded-forced pass plus the foreground pass, and its `// Fenced:` comment cites this exception by name instead of a background failure. Today it covers `AcceleratorTests.ChordCtrlShiftGOpensStats`, `ChordCtrlShiftHOpensSnapshots`, and `ChordCtrlShiftXOpensExport`. The exception never admits a test that could run through UIA patterns instead: only a test whose point is the physical press qualifies.

## Ship-with-debt gate (D00 T02 §10)

A daytime gate is complete with debt: default run green plus placement run green plus the Interactive skip count with its debt id is a complete gate, and the collector closes the debt async. Concretely: the default suite passes with zero failures and a clean foreground log, the Primary set passes with its census on primary, every Interactive test skips with the quiet-hours reason, and the skip count matches the `Night-owed` count the section recorded; the section flips the same session and never parks on quiet time. The debt id travels in the section's `Night-owed:` line and the morning report's Night debt section proves the collection; a red collection reopens through triage, never by holding the flip.

## Nightly regression run (D00 T02 §9)

The nightly run is the governed full-suite proof: three legs inside the 02:00-06:50 window, owned by the `\ScratchPad\Nightly UI` scheduled task (daily 02:30 local; action `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "R:\GitHub\ScratchPad\tools\NightlySupervisor.ps1"`, Start In the repo root, Run As DerickPayne, multiple-instances IgnoreNew, 4-hour limit, wake-to-run, interactive-token logon; all read live 2026-09-20, task operator-owned). The action runs the outer supervisor (D00 T02 §15, D00-T02-S14-PR1), which watches the run with a 14280 s timeout (PT4H minus 120 s) and publishes a minimal RED tombstone (`Status: supervisor tombstone`) when the run hangs or exits without publishing; a fresh report always stands and the supervisor relays the run's exit code, and a second supervisor stands down on its own mutex (the scheduled IgnoreNew equivalent). A manual run (`powershell -ExecutionPolicy Bypass -File tools\NightlySupervisor.ps1`, or `tools\nightly.ps1` directly with `-Force` outside the window for an accepted interruption) is the backup when the trigger is missed. The sibling `\ScratchPad\Nightly Foreground Single` task (daily 02:05, one foreground test) predates this procedure and stays outside it.

Pre-flight reaps orphaned test apps (and test hosts) whose executable lives under this checkout's `Bin/`, logging each pid plus start time; a released ScratchPad anywhere else is never touched. Leftovers from a dead run hold Bin locks (MSB3027 on the next build) and their stale windows contaminate window-enumerating tests, so the reap precedes the run at pre-flight (live-leg kills moved to job objects). A named mutex (`Global\ScratchPadNightlyRun`) serializes governed runs: a second invocation stands down with exit 0, and the reap only takes processes older than the run's own start, so overlapping runs can no longer reap each other.

Run A (default leg): one `dotnet test tests/<proj>/<proj>.csproj` per test project (Smoke, Unit, Protocol, UI) under the same gate window, `--filter "Category!=Interactive&Category!=Primary" -e SCRATCHPAD_BACKGROUND=1`, each keeping its own `run-a-<proj>.trx` (D00 T02 §15, D00-T02-S13-R2-F2: a shared solution-level trx name overwrote every project but the last), with `ForegroundLog 1800 <gate-default.log>` alongside (built first from `tools/ForegroundLog/ForegroundLog.csproj`, which no solution includes). Green needs the suite passed with zero failures AND the gate exit 0 (zero foreground holds, zero resting primary windows, zero primary births in the placement-event log, and the two logs agreeing). The gate window intentionally overruns the suite (~13 min) so the whole run stays covered; the idle tail is designed waste, and a suite that overruns its window is killed at the bell, fails the leg, and has its tree reaped (partial proof is no proof; the timeout is enforced, not a stopwatch).

Run B (primary leg): `dotnet test tests/UI --filter Category=Primary -e SCRATCHPAD_BACKGROUND=1` with `ForegroundLog 300 <gate-primary.log> --expect-primary` alongside. Green needs the suite passed AND the gate exit 0 (zero holds, at least one window resting on primary, and the placement-event log agreeing that the birth was on primary).

Interactive leg (collection): `dotnet test tests/UI --filter Category=Interactive` with no `-e` flag, owning the foreground. Green needs every collected test passed; the excused skips are quarantine skips (T02 §5 procedure) plus capability skips (host lacks hooks or a usable spooler: `HookFactAttribute`, `PrinterFactAttribute`), and quiet-hours skips fail the leg (the run owns the window, so none are excused). Enforcement is mechanical: after the leg, any skip without a QUARANTINED stamp (date plus id) or the `CAPABILITY:` reason code reds the run (the exit code alone cannot prove it, since xUnit exits 0 under skips); a missing or malformed trx is unproven and reds the run; legacy un-coded capability messages match by prefix as fallback only.

Logs land under `build/nightly/` (ignored scratch, never committed), scoped per invocation: leg transcripts `YYYY-MM-DD-HHmmss-{default,primary,full}.log` (the full log carries the Interactive collection), with the suites' stdout in `.out.log` siblings the report's Log cells name (D00 T02 §22 item 5): `YYYY-MM-DD-HHmmss-default-{Smoke,Unit,Protocol,UI}.out.log` per Run A project, `YYYY-MM-DD-HHmmss-primary.out.log`, and `YYYY-MM-DD-HHmmss-full.out.log` beside the transcripts, plus `soak-{ui,protocol}-N.out.log` per soak iteration inside the stamp directory; triage reads the `.out.log` first, since the wrapper transcript carries only the script's own lines, trx plus gate logs under `build/nightly/YYYY-MM-DD-HHmmss/`, each leg transcript recording the suite scope plus the build-time HEAD at the top (captured once after the up-front build, so mid-run commits cannot misattribute legs). A same-day second run never overwrites the first run's evidence; only the morning report keeps its day-scoped name, always written by exactly the run that just finished. Archive rule (D00 T02 §15 PR5): every publication also lands a stamp-scoped archive (`morning-YYYY-MM-DD-HHmmss[-core].md`, immutable per publication) and `latest.txt` names the current stamp, so triage resolves the freshest run without globbing. A red leg never blocks the later legs: each leg runs, the report carries every red, and only the run's exit code is red. The task appends the §5 soak loop (UI plus Protocol x5) after the legs unless `-SkipSoak` is passed; the soak is flake hunting, the legs are the regression proof.

The morning report lands at `build/nightly/morning-YYYY-MM-DD.md`: date, HEAD, trigger, a per-leg table (test counts, gate verdict, infrastructure note, log path: no cell mixes verdict classes, D00 T02 §15 PR8), a separate enforcement verdict naming any non-quarantine skips, every failure with its filed finding ref (triage appends refs after filing each failure in the owning file, before the next section starts), a captures section (screenshot, window metadata, event slice, pre-kill dumps; dumps read n/a when the leg exited before capture), and uncollected debt as information with its cause. A Night debt section carries one entry per debt open at run start (collected counts with log, or uncollected with cause), and red Interactive collections stage finding stubs under Filings for triage to file. The current report is the worked example of the format.

Failure-capture policy (D00 T02 §22 item 1, D00-T02-S15-PR21): captures (screenshot, window metadata, event slice, pre-kill dumps) stay on this machine under ignored `build/nightly/<stamp>/captures-*` with the operator profile's access, and nothing that notifies (toast, poster, result JSON) ever attaches or quotes their bytes. Redaction: window metadata keeps a title only when the process is provably the run's own, a descendant of the governed run's PID (`Get-DescendantPids`, refusing a reused parent PID by creation time; a process whose parent already exited counts as foreign), and is a kind the run launches (`ScratchPad`, `testhost`, `ForegroundLog`, `JobControl`; shells and `dotnet` never qualify because the operator's own terminals run under those names); every other title, including an operator-opened ScratchPad, writes as `[title redacted]` (`Format-WindowRow`). Secret scanning: every `.txt`/`.log`/`.json` capture is scanned after it is written (`Protect-CaptureDir`, patterns in `$script:SecretPatterns`: GitHub, Anthropic, OpenAI, AWS, and Slack token shapes, private-key headers, bearer tokens, and assigned `password`/`secret`/`api-key`/`token` values in bare, quoted, and JSON forms); a hit replaces the whole file with a redaction note naming the patterns and adds a `SECRET-SCAN` note to the Captures section, so a partial mask is never trusted; a capture the scan cannot read or rewrite is deleted (fail closed), and one that cannot even be deleted raises a `SECRET-SCAN FAILED ... do not retain this run` note plus a `SECRET-SCAN-FAILED.txt` marker beside it. Retention enforces this rather than trusting notes: `NightlyRetention.ps1 -Retain` re-scans every text capture under the source's `captures-*` directories and refuses (`retain: PROTECTION REFUSED`, nothing copied) on a marker, a secret hit, or an unreadable capture (`Test-RetainableCaptures`). Size: a capture directory over 25 MB drops its screenshots with a size-cap note. Pre-kill dumps (`dumps-<leg>/<pid>.dmp`, written by `tools/JobControl` as `MiniDumpNormal`: thread stacks plus the module list, no heap, about 0.6 MB each) are binary, so they are never text-scanned; their control is the dump type (no heap, so managed document buffers and note text, which live on the heap, are not captured; stack frames can still hold fragments) plus locality and retention like every capture. Retention: captures follow the run evidence (30 days, `NightlyRetention.ps1 -Prune`); a retained run keeps its captures under the same checksums. Screenshots are not text-scanned (a default: OCR is out of scope; cost of changing: an OCR pass per capture); their control is locality plus retention, and the Interactive leg owns the foreground while it runs, so the primary screen shows the run, not the operator's work. Staging and budget (D00 T02 §30 items 1 and 2): window lists and event slices are written under `<captures>/.staging/` and move into the capture directory only after the secret scan passes (a hit publishes the redaction note under the capture's name; staged bytes are deleted, never renamed), and leftover staging from an interrupted write is deleted unscanned by `Protect-CaptureDir` and refuses a retain. All of a run's `captures-*` directories share a 200 MB budget (`Limit-RunCaptureBudget`): over it, screenshots drop first, then dumps, then text captures, largest first within each class, and `CAPTURE-BUDGET-TRUNCATED.txt` at the run root names every dropped file with its bytes.

The Interactive leg is the night-debt collector (D00 T02 §10): at run start it snapshots open debt via `query night-debt`, resolves each debt id to its trait filter (a bare value means `Category=<value>`), and attributes the collection per debt; `-CollectDebt <id>` narrows the leg to one debt's filter, and with `-CheckOnly` it dry-runs the resolution with no side effects. Green collection appends `Night-collected:` (date, id, passed/failed/skipped, trx log path) after the debt's `Night-owed:` line for triage to commit, red collection stages finding stubs (test, first message line, test-file hint) under Filings and the debt stays open, and a zero-executed collection never closes debt (filter matched nothing: collector bug, run red). Stubs on safety or data-integrity shaped failures (data loss, corruption, integrity, disk, unauthorized, access denied, IO error) carry `REOPEN-CANDIDATE` for the agent to reopen through audit stance; the marker is a triage hint, never a decision.

Night-debt escalation lifecycle (D00 T02 §27): every open debt reads one line from one source (`night_debt_line` in `scripts/todo-graph.py`), identical in `query night-debt`, `query summary`, and the morning report, which writes the `report_block` of `query night-debt --json` (schema `night-debt/1`) verbatim, `WARN` lines included; the collector reads the same document (`Get-NightDebtDocument`, `Get-OpenNightDebts`) and fails loud on anything else. The line carries due, age, owner, state, the last log, and, when overdue, `OVERDUE escalate <owner> by <respond-by>: <next action>`. Window semantics: dates are the operator's local calendar day; a debt owed on day D is first collectable on the 02:30 collector night of D+1, so the default due day D+3 closes the third collector night, and the due day itself is not overdue. A `due <date>` override later than that default must carry a `reason <text>` chunk or it is flagged with a `WARN` line and the default kept; a malformed `due` token warns with its fallback. The owner is the latest `Night-owner` reassignment, else the owed line's `owner <name>` chunk, else the owning section's `**Owner:**` line, else the TODO frontmatter `owner:`, else `operator` (D00 T02 §35 item 1; a reassignment is how an owed-line owner changes). An overdue debt owes a response within 2 days of its due day. Lifecycle lines sit beside the owed line: `**Night-ack:** <id> (<date>, owner <name>, action <text>)` needs a date on or before today, an owner, and an action, counts only when dated on or after the escalation it answers began (so an old acknowledgement never holds a later red), reads `acknowledged`, and drops the escalation until the response deadline, then reads `response-overdue`; `**Night-accepted:** <id> (approver <name>, owner <name>, date <date>, expires <date>, rationale <text>)`, the findings-file `Risk accepted:` fields, needs every field with a date on or before today, and reads `accepted` with `accepted-by <approver> expires <date>` (never collected, so acceptance never implies the tests passed) until it expires, then `acceptance-expired` and escalates again; `**Night-red:** <date> <id> (<counts>; log <path>)`, which the collector appends on a red collection for triage to commit, resets the due window once, and a second red reads `red-repeat` and escalates with a follow-up deadline 2 days after that second red (the first repeat: a third red never moves it, D00 T02 §35 item 2), so reruns that stay red never satisfy or postpone the escalation. Every lifecycle date is a canonical `YYYY-MM-DD` real day compared as a date; a `Night-red` dated in the future or on an impossible day, or an acknowledgement or acceptance with a non-canonical or future date, changes nothing and prints a `WARN` line. Debt stays information only (§10): nothing here gates `validate`, stamps, or plan progression.

Night-debt lifecycle residuals (D00 T02 §35): red attempts are keyed by run identity, so the collector's `Night-red` line ends `; run <stamp>` and two red runs on one day are two attempts while the same run recorded twice is one (`Format-RedLine`, `Add-RedLine` in `tools/NightDebt.ps1`). A red-repeat must link the remediation it tracks: triage appends `; finding <ref>` to the Night-red line (the morning report's red entry names the owner and this next action, `Format-RedTriageNote`), or a `Night-ack` carries `finding <ref>`; a red-repeat acknowledgement with neither is ignored with a `WARN`, a red-repeat with no finding adds `file the staged finding` to its action, and the red-repeat and acknowledged lines quote `finding <ref|none>`. Acceptance governance: the approver must be one of `NIGHT_DEBT_APPROVERS` (today `operator`), the term (expires minus date) is at most 30 days, a renewal is a later `Night-accepted` line and the latest valid one reads (a later line that is incomplete or future-dated warns and never displaces an earlier valid acceptance), and `**Night-revoked:** <id> (<date>, by <name>, reason <text>)`, with every field and a date on or before today (an incomplete one warns and cancels nothing), dated on or after the acceptance voids it and the debt escalates again. Window boundaries: the owed token may be a timestamp (`owed 2026-09-17T01:00`, optionally with an offset); it reads its own recorded wall clock, never converted through the querying host's zone, so a host timezone change never moves the owed day or the trigger comparison; a debt owed before the collector trigger time named in its `collector ... HH:MM` chunk (default 02:30) is first collectable that same night and due two nights later, while a date-only owed line assumes after the trigger, so a moved trigger moves the window with it. Due extensions keep append-only history: `**Night-extend:** <id> (<date>, by <name>, due <date>, reason <text>)` needs every field with a date on or before today, the latest valid one sets the due, and the debt line quotes every one with the deadline it replaced as `extended <date> by <name> from <previous> to <due>; ...`. `**Night-owner:** <id> (<date>, owner <name>, by <name>)` reassigns the owner. The morning report writes a post-run block beside the run-start one (`Format-NightDebtPostRun`): the query re-run after tonight's collected and red lines landed, plus `<id> state collected tonight (was <state>)` for each debt open at start and closed tonight. Diagnostics, information only: a lifecycle line whose id has no `Night-owed` line prints `WARN <id>: orphan <kind> line` in the block and in the JSON `orphans` list, and two acceptances dated the same day warn as duplicates.

| 1 | `collected` | A green collection is the only proof the owed tests passed; it closes the debt whatever else was recorded | collected over accepted, over red, over ack |
| 2 | `accepted` | A valid, unexpired, unrevoked acceptance holds the escalation (a red or an ack under it changes nothing until it expires or is revoked) | accepted over red-repeat, over ack |
| 3 | `acknowledged` | An ack dated on or after the escalation start holds it until the response deadline, then `response-overdue` | ack over red-repeat (with a finding), ack without a finding ignored |
| 4 | `red-repeat` | A second red attempt escalates with a follow-up anchored on that attempt | third red keeps the anchor |
| 5 | `red` | The first red resets the due window once, after any extension | red over extension |
| 6 | `open` | Owed and not yet collected; overdue past its due day | the §27 fixture tree |

Night-debt governance residuals (D00 T02 §42): lifecycle records replay by record date, then by the record's own text (not file order), so the same lines in any order produce the same debt lines; identical duplicate lines are one record, replayed silently, and lines of one kind on one date that disagree warn as `CONTRADICTORY <kind> lines dated <day>` in the query and the report (the latest by record text reads). A `Night-owner` reassignment dated on or after the acknowledgement transfers it: the debt stays acknowledged with its response deadline and names the new owner. An accepted red-repeat still quotes its finding and `next <action>`. Window rules, aligned with §10: the owed line's recorded trigger (`collector Nightly UI 02:30`) and its own wall clock decide the first collector night (an owed timestamp reads in its recorded offset, so a DST change moves nothing), the due day closes the third collector night, and a missed collector night never extends the window. `Night-extend` is governed: the `by` must be an approver (`NIGHT_DEBT_APPROVERS`), the total past the default window is at most `NIGHT_DEBT_MAX_EXTEND_DAYS` (21), and an extension dated after the due it would move changes nothing (the response deadline stands); reds still reset the window. Closure binds to the owed tests: an owed line may name `digest <hex>` (`Get-TestNamesDigest` in `tools/NightDebt.ps1`: the first 16 hex of SHA-256 over the distinct, ordinal-sorted test names), the collector writes the executed names' digest on `Night-collected` and refuses to close on a different set (`uncollected: identity mismatch`), and the graph keeps a debt open when the digests differ; debt owed on or after 2026-09-26 must name its digest (`tools/Get-DebtDigest.ps1 -Filter <filter>` lists the filter's tests under forced discovery and prints it), or no collection closes it and it warns. Of several collected records, the latest whose digest matches closes, and the collector appends a new record past a stale one whose digest differs. A write failure never stops the collector (`Invoke-CollectedLine` turns it into a `write failed` note). Contradictions also cover reds that disagree for one run, identical `Night-extend` lines record one extension, and revocations replay in record order. A green collection whose `Night-collected` write fails, or whose closure the re-run query does not show, reads `collected-unrecorded` in the entry and the post-run block, and the run reds. A remediation finding that names a section now `[x]` never closes the debt: without a green collection it stays open and warns.

Superset and census rules: only an exact-filter green run auto-appends `Night-collected:` with leg counts; a full-Interactive green run covering a narrower `&`-only Interactive debt closes with per-test subset counts from the trx when the filter is `FullyQualifiedName`/`Name`-attributable, else stages the evidence for triage to close with subset counts, `|`/`!` filters close on exact runs only, and collected totals must equal the debt's owed count (census mismatch reds as a collector bug and the debt stays open).

Closure-safe skips are quarantine-declared only: their proof transfers to the quarantine window, while capability or other skips hold the debt open with cause (no red: the leg stays green, the debt entry plus summary carry the cause); trx subsets close only fully executed (their skips carry no reason), and exact runs census passed plus failed plus quarantine skips against owed.

The metrics store runs under a named lock, validates every line (a truncated or malformed line is skipped and reported), starts a fresh line after a truncation, and compacts with `tools/NightlyTrend.ps1 -Compact` (a `.bak` first, read back after); an executed (green or red) native row supersedes a backfill only for the same run (the same stamp, or a timer night over a timer backfill), recorded once as a `supersession/1` line. `NightlyRetention.ps1 -Prune` refuses a stamp directory whose result has no identity, no metrics row, or a row that no longer matches the result, and a metrics row is data only when its identity, stamp, real calendar night, known verdict, legs object, and whole-number counts all hold (`prune: REFUSED ... run tools/NightlyTrend.ps1 to archive it first`). Backfilled values carry a `method` and a `locator` (`<artifact>:<line>`) beside their confidence, per leg and per value (`legs.run-a.counts`, `legs.run-b.gate`, `timings.interactive`, every contributing transcript, trx, or incident line listed), metrics rows carry every field the renderer reads (environment, quarantine, scheduler, recovery, build error, timings) so a metrics-only night renders like its raw result, and one disclosure contract (`Protect-DisclosedText`: secret patterns redacted by name, user-profile and UNC paths to `[path]`, through any spaces to the next field boundary) covers provenance lines, metrics rows, incident evidence, toasts, digests, and the skipped-results line.

Trend second residuals (D00 T02 §40): a night's key is the slot `night|host` (`Get-NightSlotKey`), where the host is `hostKey`, the first 8 hex of SHA-256 over the lowercased machine name, which the nightly records (`Get-HostKey`); the schedule is not a key part, because one host serves one schedule per night and the schedule history (below) decides which nights were due. The migration from §25's offset-based night keys: results written before `hostKey` read host `legacy`, so their slot is `night|legacy`, and a legacy row beside a known host reads as a cohort change (it rebaselines once, then the new host's own series takes over). Two hosts' runs on one night are two slots, and because a run identity (stamp plus pid) can repeat across hosts, the metrics store keys a hosted row as `identity@host` (`Get-MetricsKey`; legacy rows keep the bare identity), supersession records name those keys, and an exclusion row may name `identity@host` to reach one host's run; one host's alert window and recovery notices never read another known host's nights. Two timer launches of one slot (a 02:30 trigger replayed by a DST fall-back, or a duplicate fire) keep one canonical run, and the other reads `repeated timer trigger` instead of `retry`.

Schedule history and grace: `docs/nightly-schedule-history.md` carries one row per trigger edit (`From`, `Trigger`, `Interval days`); the entry in force on a night decides whether that night was due, so an edit never rewrites earlier nights, and the task XML is the fallback only when the file is absent. A night is due-through only once its trigger plus the task's 4 h `ExecutionTimeLimit` plus 30 minutes has passed; inside that window it renders `pending`, never `missing`. The deadline is computed from each night's own date and the trigger in force that night, so a trigger near midnight keeps the previous night pending past midnight.

Cohorts rebaseline: the alert window keeps only nights in the evaluated night's cohort (OS, DPI, dotnet, host, harness, population hash) and prints `- Rebaseline: cohort changed on <night> (<changes>); N earlier night(s) leave the baseline` instead of alerting across the change; with too few same-cohort nights the series reads insufficient data (a cold start). An unknown (empty, `unknown`, or a `legacy` host) on either side compares as a change, and a missing population hash is unknown: counts no longer stand in for the hash.

| Detector | Fires when | Boundary pinned by |
| --- | --- | --- |
| runa-duration | latest > 1.25 x median of at least 5 same-cohort window nights, and at least 60 s over | `s40-boundary-exactly-125-percent`, `s40-boundary-sixty-second-floor`, `s40-boundary-exactly-five-samples` |
| runa-shift | median of the last 3 nights > 1.2 x median of the 7 before (at least 5 measured), and at least 60 s over | `s40-boundary-exactly-120-percent-shift` |
| pass-rate | latest rate < median - 2 points over at least 5 measured nights | `s40-boundary-exactly-two-points` |
| recurring-flake | an incident on the latest night also hit one of the two calendar nights before | `recurrence-needs-the-two-calendar-nights-before` |

Coverage counts unique tests: the nightly records `executedUnique`, the distinct executed test names across its legs' trx files (smoke excluded), and coverage is that count over the discovered population, so a retry or a shard never raises it and the extra executions are named (`N duplicate execution(s) not counted`); a result written before the field caps executions at the population and says `identities not recorded (count capped)`; a result whose discovery failed records `populationState = unknown` and reads `unknown (discovery failed)`.

Exclusions: an operator exclusion in `docs/nightly-exclusions.md` (`| <run identity> | <reason> |`) is intentional, not unusable. The result leaves `[native]`, `[rate]`, `[recurrence]`, `[budget]`, and `[env]`, its row reads `<night> (excluded)` with the reason, a `- Excluded:` line states the effect, it never marks its night degraded, and its baseline slot counts as missing.

Store safety: pruning re-verifies archival and deletes under the metrics lock (`Remove-ArchivedStamp`, used by `tools/NightlyRetention.ps1 -Prune -Execute`), so a result changed after the plan was drawn keeps its directory. A failed append (a full disk) is cut back to the store's prior length, so its bytes are unchanged, and the trend's metrics note names the failure; compaction can be interrupted after its backup or after its temp file and the store stays as it was, and the next compaction completes; an abandoned lock (a writer that died holding it) is taken over; a torn line after an interrupted write reads malformed, and `tools/NightlyTrend.ps1 -Restore` rewrites the store atomically from the compaction backup after validating it (the backup's `rejected/1` markers for lines compaction could not parse are counted and stay dropped, never read as corruption). A result with a lower revision than its stored row never replaces it, and the render uses the stored revision instead of the stale file (`Select-AuthoritativeResults`); the metrics note counts such stale results. Compaction sanitizes supersession records as well as rows. When a native row supersedes a backfill, fields the native row lacks (reserve, consumed, population, population hash, commit, harness, env) are taken from the backfill and the rendered row names the merge in `mergedFrom`; the live native result takes the same fields (`Add-MergedEvidence`), so the raw and metrics renders agree. Equivalence is proven on a mixed corpus (a correction, two cohorts, a malformed line) by comparing the structured metrics rows and the alert lists, not only the rendered text.

Pruned values explain themselves: each metrics row records `source` (the result file it came from), `hostKey`, and `derivation` (the row builder's version, now 2), and each night rendered from metrics prints `- Pruned night <night> (<identity>): values from <source>, derivation <n>; raw evidence pruned, metrics only`. Compaction applies the disclosure contract to every stored value and to the `.bak` backup (`Protect-DisclosedObject`); a clean row keeps its exact bytes and an unparsable line becomes a marker, so a legacy path or secret never survives a compaction.

Alert lifecycle: each alert has a stable id (`host|series`, plus the incident for a recurring flake), kept in `build/nightly/alerts.json` by `Update-AlertLedger`; a ledger that exists but does not parse fails closed (the render and the morning step report it, and the file is never overwritten). A new id opens; an open id seen again persists; every opening and closing stays pending (`notifiedOpen`, `notifiedClose`) until the morning sender accepts it (`Get-PendingAlertNotifications`, then `Confirm-AlertNotifications`), so a re-render never drops a transition and a persisting alert is raised once; each opening carries its own `occurrence` id, so a reopening on the same night is delivered on its own; an open id that stops firing closes as `recovered` on a later night, `corrected` when the same night was re-evaluated from a revised result, or `superseded` when the result it was raised on was superseded. Each known host's series is evaluated on its own (a `- Host <key>:` line heads each group when there are several), and the evaluated result's identity carries its revision, so a revised result on the same night closes an alert as `corrected`. The trend prints `- Alert lifecycle:` and the morning digest (`tools/NightlyMorning.ps1` step 1b) sends only pending transitions, keyed by the pending set so a second batch on one day is not swallowed. Alerts need no acknowledgement of their own: the RED run behind a regression is acknowledged through `tools/NightlyAck.ps1`. That is a default; the cost of changing it is one ack kind in the §39 gate.

Attribution is correlation: the alert context carries the exact revisions (`revisions <first>..<last>`), their shape from git ancestry (`linear`, `non-linear (rollback to X)`, `non-linear (divergent at X)`, or `ancestry unavailable` when history cannot answer), and ends `correlation, not cause`.

Storage policy: raw results and stamp directories follow retention (`tools/NightlyRetention.ps1 -Prune`, older than 30 days unless stamp-cited or retained); metrics rows are never deleted, so every night keeps its values, and a pruned night's confidence drops to metrics-only, which the trend states per night and per alert (`evidence ... metrics only for N`). The store's cap is 50 MB (`$script:MetricsMaxBytes`, measured in UTF-8 bytes written): an append past it is refused with a message that says to compact (`-Compact`) and then raise the cap; history is never dropped to make room.

Incident identity and lifecycle (D00 T02 §22 items 3 and 6, D00-T02-S15-PR24, D00-T02-S17-PR26, D00-T02-S17-PR27): an incident id is `INC-` plus the first 8 hex of SHA-256 over the contract key `v2|<test>|<phase>|<failure class>|<HRESULTs>|<stack signature>` (`Get-IncidentKey` in `tools/NightlyParse.ps1`). Phase is the leg family (`run-a`, `run-b`, `interactive`, `ui-soak`, `protocol-soak`), so soak iterations of one suite merge. The failure class is the exception type or the failed xUnit assertion (`Assert.NotNull() Failure`), never the printed values; unknown shapes fall back to the first message line with decimal runs collapsed. HRESULTs (`0x` plus 8 hex, from message and stack) are kept verbatim, so `0x80131505` and `0x80004005` split. The stack signature is the top three frames outside `System.`, `Microsoft.`, and `Xunit.`, method names only, with compiler-generated ordinals collapsed, so a rebuild or a line move cannot split one failure. The same ids feed the §17 trend's flake recurrence, so the contract is shared; the fixture suite pins golden ids, and any normalization change that would move them fails there first. Contract v2 starts 2026-09-25: v1 ids (test plus digit-collapsed message) do not carry over, so recurrence restarts at that boundary. Lifecycle: the cross-night ledger `build/nightly/incidents.json` (ignored scratch, atomic write with read-back) creates each incident once, appends one occurrence per stamp on recurrence (idempotent per stamp), takes the owner from the quarantine list row when the test sits there (else keeps the recorded owner, else `unassigned`), and closes an open incident only on verified recovery: its test executed and passed in the same phase on 3 separate runs with no failure between (a failure resets the streak, a run that never executed the test neither counts nor resets; `Update-IncidentLedger -RecoveryRuns`), so a flake that passes most nights cannot close and reopen nightly. A closed incident seen again reopens with its history. The report's `## Incident ledger` section lists new, recurring, recovering, reopened, and closed incidents plus the open count; triage files a finding only for `new` lines under §9's file-every-failure rule, and `recurring` or `REOPENED` lines append to the finding already filed for that id, so no incident is ever filed twice. An unreadable or unwritable ledger reds the run rather than re-minting every incident. Residuals (D00 T02 §30): a missing `build/nightly/incidents.json` reads as empty only while no result since the v2 contract (`2026-09-25-000000`) carries incidents, as incident lines or in its `ledger`-sourced lifecycle snapshot; otherwise the run reds with `rebuild: ... tools/NightlyLedger.ps1 -Rebuild`, which validates the newest `ledger`-sourced `incidentLifecycle` snapshot with `Test-ResultFile` (an invalid one refuses the rebuild, exit 1, naming the result to repair, and counts as evidence for the presence check), restores it first (identity, state, owner, occurrence stamps, pass streak, due date, finding, including incidents whose failure results aged out) and then replays only the results stamped after it, so a closed incident stays closed unless it recurred later, when it reopens with its history; a result set with no snapshot replays every result and restarts recovery from zero. The trend joins recurrence across the v1 to v2 bump through an alias map (`Get-IncidentAliases`: a v1 id maps to the one v2 id sharing its test, phase, and failure class; an ambiguous match keeps the old id) and prints it as `- Identity aliases (contract v1 to v2): ...`. An incident no quarantine row owns routes to the triage owner (`operator`) with a triage due date two days after it was first seen, never `unassigned`. Triage records each incident's finding in `docs/incident-links.md`; the ledger copies it, and every run re-lists open incidents with no link (`- Unlinked open incidents ...`) until one is recorded. The result JSON carries `incidentLifecycle` (id, test, phase, state, owner, occurrences with their stamps, firstSeen, lastSeen, passStreak, contract, due, finding per incident) beside `incidentLifecycleSource` (`ledger`, or `unavailable` when the ledger could not be read, which a rebuild never takes as state), required on the nightly's own green and red results and validated by `Test-ResultFile` wherever present (values too: occurrences a positive whole number, passStreak a whole number, contract `v2`, due `YYYY-MM-DD`, finding a section ref or commit).
